## 研究口径与结论先行

**一句话定义：**昇腾不是一家可独立交易的芯片创业公司，而是华为技术有限公司以自研 NPU、Atlas 硬件、CANN 异构计算架构、Mind 系列软件和云/集群交付绑在一起的国产 AI 计算平台；其真正的护城河不只是单颗芯片，而是把国产替代的供给、软件迁移、交付责任和开发者组织放在同一责任主体内。【S1】【S2】

本报告的主判断有两层。其一，昇腾已是国内少数可以作为**训练与推理平台基线**而非仅作为单卡候选来评估的对象；按照本库规则，CANN 可正式列为 `2.1 加速计算平台（CUDA-like）` 的次分类，而不是“待核验”。其二，这个结论不等同于“它已经与 CUDA 等价”或“某个型号必然比 NVIDIA 更快”。公开的 PyTorch 适配仓库、问题单与研究者实测恰好显示：在算子覆盖、编译链、数值一致性、分布式稳定性和故障可观测性上，迁移成本仍是机器人公司不能用宣传材料跳过的工程成本。【S2】【S5】【S6】【S7】

**行动结论（研究截止日）：**

## 一、纵向分析：从芯片项目到平台责任主体

### 1. 起点：华为的约束不是“做一块卡”，而是保住计算栈

昇腾的诞生要放在华为既有的通信、服务器、云和企业交付能力中看，而不是按一个典型 GPU 初创公司来理解。华为没有为“昇腾”设立可独立融资的主体；它是华为技术有限公司内部的产品与生态品牌。华为 2024 年报披露，当年研发支出为 **1,797 亿元人民币**，占收入 **20.8%**，研发人员约 **11.3 万人**；云计算业务（含其他华为业务板块带来的相关收入）为 **688.01 亿元人民币**。这些数字只说明母公司的持续投入与云侧承载能力，**并不拆分昇腾收入、利润或研发额**。【S1】

这一区别会改变投资判断。创业公司需要用融资和单点客户证明自己能活下去；昇腾首先要回答的反而是：芯片、服务器、驱动、编译、框架后端、通信、集群、模型和交付能否由一家公司兜底。当海外高端 AI 加速器、工具链和供给存在不确定性时，这种纵向整合有很强的市场吸引力；代价则是客户更深地进入华为的硬件、软件和服务边界，迁移的组织成本也会变高。【S1】【S2】

公开资料可确认的历史起点是：华为在 2018 年公开 Ascend 品牌及 310/910 路线，在 2019 年发布 Ascend 910。旧版新闻页目前已在华为站点改版中失效，故本报告只把这两个节点作为历史背景，并不援引失效链接作为承重性能证据；当前仍可访问的昇腾产品、驱动与开发文档则显示该路线后来延伸为加速卡、服务器、集群以及多代软件栈。【S2】【S3】

### 2. 第一阶段（2018—2020）：先定义 NPU，再补齐开发入口

早期的战略选择很明确：不是复制图形 GPU 的全部历史包袱，而是为神经网络计算建立 NPU 与配套的软件入口。硬件层从 Ascend 310（边缘/推理取向）和 Ascend 910（训练取向）起步；系统层以 Atlas 板卡、服务器和集成为载体；软件层则逐步形成 CANN、MindSpore、模型转换与开发工具。产品命名不断变化，但这一分层结构一直延续至今。【S2】【S3】【S4】

MindSpore 于 2020 年在公开代码托管平台出现；其仓库自述是可用于移动、边缘、云的开源训练/推理框架，并采用 Apache-2.0 许可证。它的意义不在于取代所有主流框架，而在于让昇腾拥有原生框架、图编译与模型表达的控制面。与此同时，华为也没有把用户锁死在一个框架上：后来 CANN 文档明确列出 MindSpore、PyTorch 和 TensorFlow 支持，说明路线从“原生框架优先”转向“原生加迁移双轨”。【S2】【S4】

这里埋下了今天的优劣势。原生栈使硬件特性、算子和图优化能更紧密协同；但主流机器人研究仍以 PyTorch、CUDA 生态和开源实现为中心。只要开发者的真实代码、调试习惯和第三方库还在后者，平台竞争就不发生在产品发布会，而发生在每一个自定义算子、动态图、分布式策略和异常栈上。

### 3. 第二阶段（2021—2023）：把“可运行”推进为“可迁移、可集群”

这一阶段的主线是 CANN 的平台化。当前 CANN 文档将其定位为 AI 场景的异构计算架构：向上连接 MindSpore、PyTorch、TensorFlow，向下服务 Ascend 处理器和编程。其公开组件包括：GE 图引擎、Ascend C 算子语言、AOL 算子库、毕昇编译器、Runtime、AscendCL，以及 HCCL 集合通信库。【S2】

这不是几个 SDK 的拼盘。GE 负责图优化、编译与执行控制；Ascend C 提供 C/C++ 风格自定义算子接口；AOL 面向神经网络与线性代数等加速库；HCCL 列出 AllReduce、Broadcast、AllGather、ReduceScatter、AlltoAll 等原语，并支持单机/多机多卡通信。文档还列出了迁移、精度调试、性能调优、离线模型编译等入口。按本库的分类准入标准，这已覆盖运行时、编译器、可扩展设备编程、加速库、主流框架后端、通信库与调试/迁移工具七项，且有公开文档、下载、样例、社区和实际硬件产品作为开发者证据。【S2】【S3】【S5】

但“接口存在”不是“迁移无摩擦”。`torch_npu` 是 Ascend/PyTorch 适配器，公开仓库存在、持续更新并保有 issue 跟踪；这证明工程入口真实存在。另一面，仓库在研究截止日前仍有开放问题：例如 issue #154 的提交者报告，在 Ascend 950PR、CANN 9.0、PyTorch 2.10 的两卡最小 GPT `torch.compile` 试验中出现超时/进程问题，且在其环境里首次前后向编译约 110 秒。该条是一个用户环境的 bug 报告，不证明所有昇腾设备或版本都不稳定；它却足以证明采购验收必须把版本矩阵与故障恢复作为一等指标。【S5】【S6】

### 4. 第三阶段（2024—2026）：大模型把竞争重心推向超节点与推理系统

大模型特别是 MoE、长上下文和高并发服务改变了竞争单位。单卡算力仍重要，却不再足以决定客户是否能上线；真正稀缺的是卡间通信、KV 缓存、Prefill/Decode 分离、调度、监控、模型服务与运维责任。昇腾的公开栈已将 MindIE（推理）、MindCluster（集群）、MindSpeed（训练/性能相关工具）、MindStudio（开发调优）等置于同一开发者门户，官方站点还列出服务器兼容目录、伙伴计划、模型与开发资源。【S3】

CloudMatrix384 是这一阶段最有代表性的系统证据。一篇由华为云作者发布的公开论文描述：该 SuperPod 由 **384 颗 Ascend 910 NPU** 与 **192 颗 Kunpeng CPU** 组成，采用 UB 网络；论文声称其服务 DeepSeek-R1 时的 Prefill 与 Decode 性能达到特定结果。由于作者及系统属于华为云，该证据等级只能是“华为关联方的工程披露”，不能当成独立第三方基准，更不能拿其 token/s 直接替代机器人 VLA 训练或端侧实时控制的容量计算。【S7】

然而，这篇论文仍揭示了产品方向：昇腾正从“卖 NPU 服务器”转向“以超节点、网络、缓存、服务框架和模型适配一起交付”。这也是华为和多数国产单芯片厂商之间真正拉开差异的地方。单卡可被比较，系统责任很难被一张参数表复制。

### 5. 商业化、融资与团队：强资源不等于可拆分财务

昇腾没有对外披露独立融资轮次、估值、独立收入、客户回款、出货数量或可分离股权。华为年报可被用来确认公司级研发投入和云业务收入，不能被重述为“昇腾融资”或“昇腾营收”。同样，华为员工持股和公司整体组织不构成昇腾业务线的投资人表。对投资团队而言，这不是资料整理上的小瑕疵，而是交易边界：任何“投资昇腾”的提案都必须先回答所投的究竟是华为集团、某个生态伙伴、服务器集成商，还是只是一份采购合同。【S1】

公开材料也未给出可审计的昇腾核心团队名单、人数和 IP 归属分工。可以确认的是：CANN、MindSpore、Ascend/PyTorch 等都有对外文档和开源组织；不能因此把全部贡献者视为华为雇员，或据此推断人员稳定性。该缺口应在任何深度战略合作前通过 NDA 尽调，而非在报告中虚构“华为芯片团队”的人力资产。

## 二、横向分析：不是四张加速卡，而是四种责任边界

### 1. 竞争场景判断

昇腾处于竞争者充分的场景。选择 NVIDIA、寒武纪、壁仞科技、沐曦四个参照物，不是把它们的芯片逐项排位，而是分别代表：全球 GPU 与 CUDA 事实标准、国内上市 NPU 竞争者、国内数据中心 GPGPU 平台、国内通用 GPU 平台。机器人公司的真实替代选项还包括“继续保留 CUDA”“以云服务购买而非买卡”“把工作负载拆分到端/边/云”，因此不存在单一的胜负指标。【S8】【S9】【S10】【S11】

| 对照对象 | 产品哲学与可购买单位 | 软件/生态位置 | 对昇腾的优势或短板 | 对机器人公司的正确比较方式 |
|---|---|---|---|---|
| NVIDIA | GPU、CUDA、网络与整机/云生态 | CUDA 文档、工具、第三方库和全球研究代码构成默认接口【S8】 | 优势在成熟开发者与广泛兼容；供给、合规、价格和区域可得性须单独评估 | 以现有 PyTorch/CUDA 代码的 JCT、bug 密度、升级风险和 TCO 作迁移基线 |
| 华为昇腾 | NPU、Atlas 硬件、CANN、Mind 系列及云/集群 | 自有编译、算子、通信、框架后端和开发入口【S2】【S3】 | 优势是国产全栈和单一责任主体；短板是 CUDA 非同构、迁移与版本矩阵成本 | 以受控 POC 验证，而非比纸面峰值算力 |
| 寒武纪 | MLU 加速器与 Neuware 平台 | 国内 NPU/软件平台竞争者，主体为上市公司【S9】 | 交易上可做股权与二级市场研究；硬件与软件仍须按实测 | 对同一模型、同一精度、同一集群网络下的可用性和支持 SLA |
| 壁仞科技 | 数据中心 GPGPU 与软件栈 | 更接近 CUDA-like GPU 路线【S10】 | 对 CUDA 风格工作负载的概念迁移可能更自然；产品可得性、生态和服务边界另验 | 把迁移工作量、训练稳定性和供应链同昇腾并列，而非把 GPU 标签当结论 |
| 沐曦 | 云端通用 GPU 与计算平台 | 亦以国产通用 GPU 软件生态竞争【S11】 | 与昇腾共同争夺国产训推项目，但架构和工具链不同 | 用实际 VLA/VLM 训练、仿真、离线数据处理和推理任务比较 |

### 2. NVIDIA：真正的参照物是工作流惯性

NVIDIA 的难点不只是某一代 GPU 的绝对性能。CUDA Toolkit 的长期文档、编译工具、库、分析器和被研究框架默认支持的后端，已经成为大量模型代码的隐含假设。【S8】这会表现为两种成本：第一种很显性——迁移算子、容器、驱动、通信和监控；第二种更隐性——上游仓库更新后，团队是否还需持续维护私有 patch。

昇腾面对 NVIDIA 时不应承诺“无感替换”。它合理的价值主张是：在中国本地可交付、供应保障有意义、又能接受适配工程的工作负载里，用可控的迁移成本交换硬件与服务的替代路径。对机器人公司，优先挑模型结构稳定、算子集合可控、数据不宜出境或需要私有部署的批量任务；不要以最前沿、每天改结构的研究主线作为第一批迁移对象。

### 3. 寒武纪：同为 NPU，并不消除平台风险

寒武纪是昇腾更直接的国产 NPU 对照。它拥有独立上市主体和自己的产品/软件叙事，因此在股权、交易结构和对单一大厂依赖的讨论上与昇腾完全不同。【S9】但对使用方而言，两者共享一个核心问题：NPU 的效率依赖编译器、算子与模型图的共同成熟度，而非只看标称 TOPS。

这使昇腾的相对位置颇微妙。它的组织规模、服务器/云/网络整合与开发门户，使其更像一个项目总包方；寒武纪可能更适合作为独立芯片供应选项。前者降低多供应商扯皮，后者保留更多议价与组合空间。机器人公司应避免先问“谁更国产”，而是先问故障发生时谁能给出日志、复现环境、修复版本和责任期限。

### 4. 壁仞与沐曦：GPU 路线把迁移难题留在不同的位置

壁仞与沐曦代表国内数据中心通用 GPU 的另一路径。二者将自己定位于通用 GPU/数据中心计算平台，而非昇腾式 NPU；从开发者心理上看，这通常更接近现有 GPU 编程和模型训练习惯。【S10】【S11】但“更接近”不是“已经兼容”：GPU 软件栈的库覆盖、分布式、容器、调试、性能分析、驱动稳定性、供货与服务依旧需要逐项验收。

对昇腾而言，GPU 路线的存在反而强化了其差异化：华为卖的是更完整的国产基础设施关系，而不是仅争取某个 CUDA 翻译器的兼容分数。对机器人公司，最佳做法是将昇腾与一款国产 GPU 同时放进基准池：前者检验 NPU 全栈总包能力，后者检验研究代码的迁移摩擦。只选其中一家，会把“架构风险”和“供应商风险”绑死在一起。

### 5. 开发者视角：入口已经成形，体验仍以版本为单位

昇腾的正面证据是可见的：CANN 开放 Ascend C、自定义算子、运行时、图开发、HCCL、调优/迁移工具；`torch_npu` 公开维护；MindSpore 是公开开源框架；官方门户还提供模型、下载、文档、论坛、培训与兼容目录。【S2】【S3】【S4】【S5】这足以把它和仅有 SDK 或封闭演示的早期项目区分开。

负面证据同样可见。公开 issue 中存在 `torch.compile` 超时、算子支持、框架行为与版本适配问题；独立预印本对 16 卡 Ascend 910 上 MoE/VLM 推理的现场研究报告了算子/特性不完整、并行脆弱、数值与设备级故障、可观测性不足等问题。后者是作者的特定系统研究，不应升格为平台总判决；它却与“所有项目都应以锁定的硬件—固件—CANN—PyTorch—插件版本验收”的工程常识相互印证。【S6】【S12】

因此，开发者体验不能被一个“兼容 PyTorch”的勾选框概括。应将它拆成：模型能否导入、算子能否运行、精度是否守住、单机性能是否达标、多机通信是否稳定、报错能否定位、升级能否回退、外部依赖是否持续跟随。只有八项都过关，才叫生产可用。

## 四、横纵交汇洞察：平台的时间比芯片的时间更长

### 1. 历史如何塑造当前位置

昇腾今天能进入“平台基线”而不是“国产卡观察名单”，来自一个持续多年的选择：先由华为承担芯片与系统，再把 CANN、MindSpore、PyTorch 适配、HCCL 和集群/推理工具补成连续栈。这个选择的收益是显而易见的——客户在国产化项目中可以找到一个负责硬件、软件和交付协同的主体。CloudMatrix 的系统论文是这一思路走到极端的缩影：多芯片、多网络、多服务组件被组织成一个服务单元。【S2】【S3】【S7】

同一历史也制造了包袱。CUDA 的优势来自数以十年计的第三方代码与研究惯性；CANN 则必须在快速变化的 PyTorch、Triton、编译模式、MoE 和多模态模型之后持续追赶。每增加一个自定义算子、每升级一次框架，NPU 的专用优化都有机会成为性能优势，也可能变成兼容债务。公开 issue 和独立研究不是偶发的 PR 风险，而是这一结构性张力的日常表现。【S5】【S6】【S12】

### 2. 三个情景

**最可能情景（概率判断：中高）：成为中国境内“可采购的第二平台”，而非 CUDA 的全球替代品。** 华为继续将昇腾、云、服务器、集群与模型适配组织为本地项目的单一责任主体。适合的工作负载是需求稳定、可被版本冻结、重视交付与供应安全的训练/推理任务。它的成功不需要在每个开源研究分支上胜过 NVIDIA，只需让足够多的客户在受控场景中可预测地上线。

**危险情景（概率判断：中）：硬件推进快于软件可验证性。** 若型号、超节点或生态宣传快于算子覆盖、版本兼容、数值回归、HCCL 可观测性和现场支持，客户会将工程成本留在自己的平台团队。短期订单可能仍存在，长期却会形成“只有原厂项目组能跑”的锁定，机器人公司会被迫为每次模型创新做特例迁移。公开 bug 和现场研究正是应当提前建立验收纪律的理由。【S6】【S12】

**乐观情景（概率判断：中低）：从国产替代项目走向可复用的异构训练/推理标准。** CANN 的开放算子、PyTorch/Triton 路径、HCCL 及 CloudMatrix 系统能力若持续减少版本摩擦，昇腾可以在 MoE、长上下文、批量推理和中国本地云/私有化部署中形成结构性优势。前提不是发布更高峰值，而是把可重现性能、数值协议、故障恢复和独立开发者支持变成日常产品能力。

### 3. 对人形机器人的战略含义

机器人公司不应把昇腾视为“替代 GPU 的一笔采购”，而应视为**训练与推理供应链的一个分支**。训练侧可把大规模数据清洗、视觉回放、仿真批处理、固定版本 VLM/VLA 微调作为第一批候选；在线侧可把园区/工厂私有推理、视频后处理和知识服务作为候选。低时延动作控制、机载多传感器、功能安全和极端散热则必须另建证据链，当前不以数据中心成果外推。

建议建立不依赖任何单厂商的“模型—算子—性能—成本—可靠性”台账：保存原始 PyTorch 实现、ONNX/中间表示、测试数据版本、精度容差、算子 fallback、容器哈希、通信拓扑、驱动/CANN/框架组合、故障注入与回退脚本。这个台账比拥有某一种国产卡更接近供应安全，因为它让 NVIDIA、昇腾及国产 GPU 都可以在同一验收框架里竞争。

- **3.3 算力中心集成、3.5/3.6 集群软件：不列为正式次类。** 超节点和 MindCluster 是平台交付组成，而非当前可分离、以此为主价值创造的独立公司/产品线证据。若未来研究对象转为华为云或独立集成业务，应另行分类。
- **5.1/5.2/5.3：不列为正式次类。** MindSpore 与 MindIE/MindSpeed 的确涉足框架、推理与分布式工具，但对“华为（昇腾）”这一公司条目的主收入承载物仍是 NPU 平台；这些功能已被 `2.1` 充分表达，额外列类会制造重复归类。
