# 上海密瓜智能科技有限公司（密瓜智能）横纵分析报告

> 研究截止日：2026-08-09｜研究类型：单公司横纵研究（严格法人边界）｜唯一研究对象：上海密瓜智能科技有限公司

## 结论摘要

**本报告唯一研究主体是上海密瓜智能科技有限公司。** 该公司官网的“公司”页写明其于 2025 年 1 月 23 日成立，围绕异构算力虚拟化、调度、统一管理与 Kubernetes GPU 资源共享提供技术研发和服务；该页面并称张潇为法定代表人。[公司与产品页](../raw/sources/2026-08-09-dynamia-official-company-products.md) 同一网站的隐私政策却明示，`dynamia.ai` 的运营者是 **DYNAMIA INTELLIGENCE PTE. LTD.**（新加坡）；页脚也作相同标示。[网站运营与商业线索](../raw/sources/2026-08-09-dynamia-official-website-operator-and-commercial-leads.md) 因此，官网的企业版、平台版、试用/报价表单、案例、海外化和“原厂 SLA”材料，能说明一个以 Dynamia 品牌出现的商业化主张，但**不能自行证明**由上海公司签约、开票、收款、交付、承担 SLA，或由该公司拥有代码/IP。

HAMi 则应再独立看待。CNCF 记载该项目在 2024-08-21 被接受、在 2026-07-02 达到 Incubating 成熟度；GitHub 仓库把它描述为 Kubernetes GPU 虚拟化与异构加速器调度项目，使用 Apache-2.0 许可证，并写明由 contributors 治理、版权归属为 `Contributors to HAMi` / LF Projects 体系。[CNCF 项目状态](../raw/sources/2026-08-09-hami-cncf-project-governance.md) [仓库、维护者与许可证](../raw/sources/2026-08-09-hami-github-license-and-maintainers.md) 虽然维护者名单把 Li Mengxuan、Xiao Zhang 的 `Employer` 填为 `dynamia.ai`，并且上海公司官网称两人为创始团队和 HAMi 维护者，但这仍不能替代劳动关系、职务发明、CLA、商标、企业版差异代码或项目商业授权文件。HAMi 的采用/贡献者/案例更不能直接变成上海公司的客户、合同或海外收入。

**分类结论：建议把上海密瓜智能科技有限公司暂列为 `4.1 跨厂商训推算力调度平台（主标签，条件性）`，中低置信；`4.3 推理跨 XPU 异构调度`不成立。** 其理由是官网对上海公司和其产品方向的自述、HAMi 的多加速器 Kubernetes 调度能力，以及融资材料均指向同一业务意图；但商业产品网站由新加坡公司运营，上海法人对企业版/平台版、销售合同和服务收入的承接没有闭环。HAMi 对 vLLM 等生态的集成不等于已经证实“跨 XPU 推理路由”、推理 SLA、P/D 分离、跨设备故障切换或按 Token 计费能力，故不授予 4.3 标签。

对人形机器人公司，现阶段不建议生产单一来源采购、直接估值投资或整体并购。适宜动作是：先在本地/私有云受控 PoC 中验证异构卡资源切分、容器隔离、批训练队列与推理服务共池，再要求**上海公司作为合同和支持责任主体**提供企业版代码范围、开源合规、许可/SLA、数据处理、升级退出与故障责任文件。PoC 通过也只说明技术可用性；未完成中国/新加坡主体、HAMi 治理和企业版 IP 的穿透前，不能把它转为确定商业资产。

### 1.1 本次隔离规则

1. **网站运营不等于中国经营承接。** 定价页只写“按集群规模与复杂度定制”，试用页提供 License、部署、报价/合作选项；隐私页面却指向新加坡网站运营者，且未公开订单条款。它不能证明任一法人已与任何客户签署合同。[网站运营与商业线索](../raw/sources/2026-08-09-dynamia-official-website-operator-and-commercial-leads.md)
2. **项目维护不等于可收购 IP。** 公开仓库的 Apache-2.0 许可和 contributor 版权安排，决定 HAMi 是可利用的开源底座，不是可将整个项目独占买断的资产。企业版若有差异化，需单独清点私有代码、商标、构建流水线、镜像、支持权和员工发明链条。[仓库、维护者与许可证](../raw/sources/2026-08-09-hami-github-license-and-maintainers.md)
3. **项目案例不等于公司订单。** 官网案例中出现的贝壳、DaoCloud、顺丰科技、PREP EDU、蔚来、SNOW、招商银行等，只支持“该网站将它们呈现为使用 HAMi 的案例”；没有客户方公告、合同、验收、金额、付款、签约方或持续支持证明，不能录为上海公司的客户或新加坡公司的海外收入。[官网案例目录](../raw/sources/2026-08-09-dynamia-official-hami-case-studies.md)
4. **融资新闻不等于 cap table。** 投资界和拙朴投资的页面分别支持种子轮和天使轮的公开表述，但没有股权比例、估值、交割、到账、优先权或最新股东名册。[种子轮报道](../raw/sources/2026-08-09-dynamia-pedaily-seed-financing.md) [天使轮公告](../raw/sources/2026-08-09-dynamia-zipcapital-angel-financing.md)

## 3. 纵向分析：项目先行、法人后设、商业主体待闭环

### 3.1 2018—2024：HAMi 的前史是技术谱系，不是上海公司的公司年龄

HAMi 公共项目指标记载首个提交为 2018-03-12；README 又指出项目曾名为 `k8s-vGPU-scheduler`。这可以解释团队为何把“GPU 虚拟化与异构调度”作为起点：它不是凭一张商业方案才出现的概念，而是 Kubernetes device plugin、调度扩展、webhook 与设备后端逐渐组合出来的工程项目。[项目历史](../raw/sources/2026-08-09-hami-github-project-history.md) [仓库、维护者与许可证](../raw/sources/2026-08-09-hami-github-license-and-maintainers.md)

但在法人研究中，2018 不是上海密瓜智能科技有限公司的成立年份。CNCF 的独立项目页显示，HAMi 于 2024-08-21 进入 CNCF，这个节点发生在上海公司官网所称的 2025-01 成立之前。[CNCF 项目状态](../raw/sources/2026-08-09-hami-cncf-project-governance.md) 正确的叙述应是：创始团队和开源项目有先行技术路径；是否有代码、商标、员工、客户、合同或商业权利在公司成立时转入上海法人，尚缺权属文件。把“项目累积八年”写成“中国公司已有八年营收/资产/客户”，会制造严重的尽调幻觉。

技术层面，HAMi README 描述的架构包括 mutating webhook、scheduler extender、device plugins 和容器内设备虚拟化组件；资源请求可按显存、算力或设备数切分，并支持设备感知、Binpack、Spread、拓扑感知等策略。它适用于共享 Kubernetes AI 集群、混合训练/推理工作负载和多厂商加速器的同一分配工作流。[仓库、维护者与许可证](../raw/sources/2026-08-09-hami-github-license-and-maintainers.md) 这给出上海公司的技术“可出身”解释，却也决定其护城河不能仅靠一个开源安装包：Apache-2.0 允许用户和竞争者使用、修改及分发满足条件的代码。

### 3.2 2025：上海法人设立与种子融资，把维护能力包装成企业服务尝试

官网把 2025-01-23 作为上海公司的成立日，并称张潇、李孟轩领衔；GitHub 维护者文件中 Li Mengxuan 和 Xiao Zhang 的 Employer 均为 `dynamia.ai`。两处材料相互呼应到“团队与项目具有连接”，但仍停在网页公开身份层，未能确定二人的劳动合同究竟签给上海公司、新加坡公司还是其他主体。[公司与产品页](../raw/sources/2026-08-09-dynamia-official-company-products.md) [仓库、维护者与许可证](../raw/sources/2026-08-09-hami-github-license-and-maintainers.md)

2025-03-27，投资界报道上海密瓜智能科技有限公司完成“超五百万”种子轮，投资方包括 DaoCloud 道客、奇绩创坛及其他种子投资人；该报道也转述管理层“预计在 2025 年实现百万元级别的营收突破”。[种子轮报道](../raw/sources/2026-08-09-dynamia-pedaily-seed-financing.md) 前者可作为融资事件线索，后者只能当作预测，不能倒推截至截止日已实现的收入、ARR、现金流或客户数。

这一阶段的商业逻辑很直接：开源 HAMi 解决“整卡给小任务”与国产/海外设备接口分散的问题；公司则希望销售加固版本、支持、部署和统一管理。障碍也同样直接：开源项目存在数位不同雇主的 committers，且商业化页面尚不能明确绑定上海公司。对投资者而言，所谓“从开源到商业化”的关键不在融资新闻，而在谁能对客户承担许可证、漏洞响应、性能承诺和赔偿责任。

### 3.3 2026：天使轮、产品化页面与 CNCF Incubating 同时推进

2026-01-06，拙朴投资官网称上海密瓜智能科技有限公司完成“数千万元”天使轮，复星创富领投，拙朴投资、种子投资人和产业方跟投。公告没有披露具体金额、估值、占股、交割或当前股东，因此融资表必须保留“数千万元”的原始口径。[天使轮公告](../raw/sources/2026-08-09-dynamia-zipcapital-angel-financing.md)

公司网站的产品页在同一时期展示三层路径：开源 HAMi、HAMi 企业版和 HAMi 平台版。它把企业版写为提供加固、运维和 SLA 的商业发行版，把平台版写为多集群控制面、配额、可观测与生命周期管理；两款页面产品均标示 `v2.9.0`、2026-05-20 发布。[公司与产品页](../raw/sources/2026-08-09-dynamia-official-company-products.md) 这是从“项目维护”走向“可收费支持层”的合理产品方向，但它首先是网站声明。试用/报价页面的表单由网站运营者承接，且订单/服务条款不可见，所以不能把产品发布日期写成上海公司已经完成了某个客户的商业交付。

2026-07-02，CNCF 把 HAMi 升至 Incubating 成熟度。[CNCF 项目状态](../raw/sources/2026-08-09-hami-cncf-project-governance.md) 这个节点的战略含义是双刃剑：一方面，基金会治理与中立性降低了用户选择开源底座的心理门槛；另一方面，越中立的项目越不能天然被单一商业公司独占。上海公司未来能否占据价值池，取决于其能否把上游响应速度、经过验证的多 XPU 兼容、离线交付、可观测、支持 SLA 与可审计合规变成付费服务，而不是仅把项目成熟度当作公司收入证明。

## 4. 产品、商业化和 HAMi IP：应拆成三本账

### 4.1 第一账：开源 HAMi 的可验证能力

HAMi 是 Kubernetes 原生的虚拟化/调度中间件：设备共享、资源隔离、设备感知调度和异构设备纳管是其公开核心功能。README 还列有对 vLLM、Volcano、Kueue、Prometheus、Grafana 和 NVIDIA GPU Operator 的生态集成。[仓库、维护者与许可证](../raw/sources/2026-08-09-hami-github-license-and-maintainers.md) 对机器人训练平台而言，这一层的价值在于：把闲置加速卡切成可治理资源，让小规模视觉模型训练、仿真批任务、数据处理和在线推理尝试共用池子，而不必改变应用代码。

需要避免的误解有三种。第一，README 的“支持多类设备”并不等于在任意模型、任意驱动、任意集群上性能和隔离语义一致；具体设备能力会随厂商、型号、驱动和代际变化。第二，资源分割与分布式训练调度不是一回事：后者还需要 gang/queue、网络拓扑、存储、通信库、故障恢复和多节点弹性。第三，出现 vLLM 集成不等于跨 XPU 推理层已经处理模型二进制兼容、KV cache 路由、流量切分或 P/D 分离。因此 HAMi 是强可用的开源候选底座，不是已经被证明的跨 XPU 推理服务。

### 4.2 第二账：企业版/平台版是待验证的商业附加层

网站声称企业版可提供更强隔离、超卖、优先级、拓扑亲和和 Volcano 集成；平台版还声称多集群 GUI、监控/告警、生命周期管理、多租户、计量计费、OpenAPI、离线部署及“7×24 交付 SLA”。[公司与产品页](../raw/sources/2026-08-09-dynamia-official-company-products.md) 这套组合如果属实，才是可向机器人训练/推理团队销售的管理面价值：不仅分 GPU，还能管理租户、预算、故障、可观测和跨集群资源。

但当前公开证据只到“网页功能矩阵”。没有企业版的源代码范围、与上游的差异补丁、二进制/镜像签名、授权策略、定价、工单系统、漏洞响应 SLA、客户实测、版本兼容或支持责任主体。并购或采购中应将这些逐项写入资料清单；否则所谓“企业版”可能只是可被上游版本替代的包装，也可能真实存在但由目标法人以外主体持有或服务。

## 7. 横向分析：它面对的不是单一竞争者，而是四层可替代栈

密瓜智能的产品叙事同时覆盖了设备虚拟化、调度、多集群管理和企业支持。横向比较若只找另一家“异构调度创业公司”，会遗漏更现实的采购替代：用户可能继续使用开源 HAMi；用批调度器补上队列；用通用 Kubernetes 调度/混部组件解决部分资源问题；或在 NVIDIA-only 环境里接受原厂工具。以下比较只对技术边界下判断，不对他方法人的融资、客户或市场份额作无来源推断。

| 路线 | 官方可见核心定位 | 与密瓜/ HAMi 的关系 | 对机器人公司的含义 |
|---|---|---|---|
| **HAMi 开源上游** | GPU 虚拟化、异构加速器调度、设备共享/隔离与 Kubernetes 集成。 | 是上海公司产品主张的上游基础，也是最强的零许可费替代。 | 若内部平台团队能力足够，可先以开源版本验证；企业版只有在可量化的支持、隔离、管理和交付价值成立时才值得付费。 |
| **Volcano** | 面向计算密集任务的云原生批调度；统一调度、队列、多集群、GPU/NPU 异构设备、Gang/Fair-Share/Binpack/拓扑感知等。 | 既可与 HAMi 集成，也会在队列、训练任务编排和资源策略上覆盖用户的一部分需求。 | 对大规模训练、仿真、数据处理，Volcano 是必测的底座；HAMi 需要证明“设备切分/虚拟化”带来的增量，不能以 Volcano 集成冒充独立训练调度能力。 |
| **Koordinator** | Kubernetes 上微服务、AI 和大数据的 QoS/混部调度，强调弹性配额、打包、超卖、共享和隔离。 | 在集群利用率、优先级、超卖、隔离方面存在替代或互补。 | 如果痛点主要是 CPU/GPU 混部和 QoS，先比较 Koordinator 组合的运营复杂度；若痛点是多加速器设备分割，HAMi 更贴近。 |
| **NVIDIA GPU Operator + vGPU/MIG/Time-Slicing** | 自动部署和管理 NVIDIA driver、device plugin、Container Toolkit、GFD、DCGM 等；文档列 NVIDIA vGPU、MIG 和 Time-Slicing。 | NVIDIA 单一栈的原厂基线，不声称跨厂商统一抽象。 | 集群若长期单一 NVIDIA，原厂路线更容易获得驱动/兼容支持；密瓜的跨厂商价值应靠混合卡真实可用性证明，而不是泛化营销。 |

Volcano、Koordinator 与 NVIDIA 的技术表述均来自各自官方页面。[代表性替代方案官方资料](../raw/sources/2026-08-09-heterogeneous-scheduling-alternatives-official.md) 其中 Volcano 和 Koordinator 更像部分层级的互补/替代，NVIDIA 路线则是硬件单一时的替代基线；它们不应被粗暴写成“一模一样的商业竞品”。

### 7.1 密瓜智能当前的相对位置

它的正面位置在于：HAMi 不是纯粹的控制面 dashboard，而是下沉到 Kubernetes 设备共享、显存/算力限制和异构设备调度的工程项目。对同时有 NVIDIA、昇腾或其他国产卡的机器人训练场景，统一资源请求和共享策略确有实用价值。若企业版能够提供可信的离线交付、升级回滚、驱动兼容、监控、审计、故障支持和多集群运营，它会在“开源组件拼装”与“单厂商封闭栈”之间形成服务层位置。

劣势也来自同一历史根源。项目因开源与 CNCF 治理获得生态扩散，但开源许可证使核心能力难以形成排他权；而商业层又出现上海/新加坡运营边界未清。对用户来说，迁移成本因上游开放而较低；对买方来说，团队能力可能有价值，项目本身却不能按照专有软件全额收购。对投资者来说，价值应主要放在服务收入、企业版差异、维护响应、渠道和客户留存，而不是把社区规模折现为公司收入。

### 7.2 横向比较后的采购问题清单

一项合格的机器人 PoC 应以同一集群、同一应用负载对比“HAMi 开源”“HAMi 企业/平台版（若上海公司承接）”“Volcano/Koordinator 组合”以及“NVIDIA 原厂栈”。至少观察：

- 两种以上加速器的资源声明、驱动/运行时适配、显存和计算隔离语义是否一致；
- 多租户训练、数据预处理、仿真和推理服务混跑时的作业排队、抢占、干扰和恢复；
- 节点故障、驱动升级、版本回滚、离线环境和安全漏洞修复的责任边界；
- 计量、配额、审计、成本归集以及 API/控制面与现有 MLOps 的连接；
- 并非只测平均利用率：须测训练成功率、排队时间、推理尾延迟、故障恢复时间与运维工时。

没有这些对照，任何“利用率提高”宣传都不足以支持采购、估值或并购结论。

## 9. 横纵交汇：开源的优势，也定义了交易的边界

纵向看，密瓜智能不是传统 SaaS 从一个封闭产品开始卖许可证；它是一个先有开源项目、后有 CNCF 项目身份、再设立公司并尝试把支持和多集群管理商品化的团队。这个顺序解释了它今天最可信的优势：维护者接近上游，能理解设备插件、调度策略和多厂商适配的真正摩擦。也解释了它最不应被忽视的弱点：核心项目的可得性很高、贡献者并非都属同一雇主，且网站和商业线索出现中国/新加坡主体不闭环。

横向看，用户不需要在“密瓜”与“什么都没有”之间选择。用户可以直接部署 HAMi，搭配 Volcano 做训练队列，用 Koordinator 做混部，再在 NVIDIA 集群用 GPU Operator 管理驱动。这种可替代性迫使企业版必须在可验证的生产运营上获胜：异构硬件兼容的深度、离线环境的交付、升级与回滚、可观测与审计、支持响应、可量化成本，缺一不可。

因此真正的判断并非“HAMi 会不会成功”，而是“上海密瓜智能科技有限公司能否合法且可持续地把项目上游能力转为可承诺、可签约、可留存的企业服务”。在目前证据下，答案只能是**待验证**。

### 三个剧本与触发条件

| 剧本 | 发生逻辑 | 观测触发条件 | 对机器人公司的动作 |
|---|---|---|---|
| **最可能：开源采用扩大，商业服务有限但可用** | HAMi 的中立性继续推动安装；上海公司能取得一部分中国企业交付，但产品/网站/海外主体边界仍复杂。 | 上海公司能出示本地合同、SLA、至少两类加速器生产兼容与续费，但新加坡关系/企业版 IP 仍未完全穿透。 | 维持退出式 PoC；把上游 HAMi 当可替换组件，合同要求源码/镜像托管、迁移权和数据边界；不形成单一来源。 |
| **最危险：商业承接与专有资产不能闭环** | 开源层被用户或集成商直接采用，网站获客、海外渠道、产品镜像/服务责任落在未披露主体；上海公司难形成可计价收入。 | 无法提供中国/新加坡授权、企业版代码/商标归属、客户合同和回款；核心维护权限或人员不随交易可转移。 | 停止生产采购、直接投资和整体并购；仅在 Apache-2.0 上游许可允许范围内自主集成，并做好替代方案。 |
| **最乐观：企业服务层闭环并取得跨 XPU 可复现优势** | 上海公司明确获得企业版/IP/销售支持授权，形成可审计多芯片客户交付；新加坡公司是受控的海外运营或被清晰授权。 | 法人关系、CAP table、IP、劳动关系、上游治理、三家以上具名/匿名可核验订单和回款闭环；跨 XPU 训练/推理 PoC 通过且有性能/SLA；若要申报 4.3，额外提供路由/PD 分离生产证据。 | 可谈小额战略投资或区域合作，采购仍采用双供和退出条款；并购仅评估可转让企业版资产与关键团队，不把 HAMi 公共项目整体估价。 |

## 10. 面向人形机器人公司的分项建议

| 决策 | 建议 | 前置条件与原因 |
|---|---|---|
| **采购** | 只做受控 PoC，不进入训练集群或量产推理的单一来源 BOM。 | 签约方必须是上海公司或经披露、可追偿的授权主体；明确 License、SLA、数据处理、升级/回滚、漏洞修复、模型/数据隔离、退出和源码/镜像可得性。先证明多 XPU 组合下的稳定性。 |
| **合作** | 可合作做 Kubernetes 异构资源池 PoC，范围限定在资源虚拟化、训练/仿真队列和可观测。 | 与 HAMi 上游、Volcano/Koordinator、GPU Operator 做盲测对照；不要把“兼容互认”替代为实测或订单。不得将机器人数据、模型权重传给未澄清的数据处理主体。 |
| **投资** | 暂不直接估值入股；完成 P0 主体/IP/合同/收入尽调后才评估小额战略投资。 | 需要融资交割与现时股权、关联方、企业版资产、客户收入和留存、团队劳动关系及多芯片交付能力；不得按开源项目社区规模估值。 |
| **并购** | 不建议整体并购；仅在权属清晰后考虑收购企业服务资产或吸收关键团队。 | Apache-2.0 项目和多雇主贡献者不能整体“买断”。先确认员工、仓库权限、商标、私有补丁、客户 MSA、支持系统和新加坡关联资产均可交割。 |
| **自研** | 不应第一时间重写 GPU 虚拟化；应保留自有的资源目录、调度策略、计量/审计、供应商适配测试和 MLOps 接口。 | 利用上游 HAMi 做可替换底座，同时把业务关键控制面留在内部；如果外部方案无法提供跨 XPU 推理证据，则将路由、容量规划与 PD 分离作为内部能力路线，而不是假设供应商已具备。 |

建议的下一步不是联系公司或启动交易，而是整理一份离线尽调清单与 PoC 验收表：主体关系图、企业版/SLA 合同、IP/开源清单、客户合同/回款、XPU 兼容矩阵、故障演练和安全/数据处理证明。完成这些材料，才能把“开源维护者团队”升级为可进入机器人生产基础设施和资本决策的公司标的。
