## 结论先行

趋动科技不是一家 GPU 云，也不是已经被充分验证的“跨 XPU 调度平台”。它的承重能力是将 NVIDIA GPU 从“随服务器附着、按整卡独占”的资产，转换为可切分、可远程调用、可排队并能在数据中心内统一治理的虚拟资源。OrionX 的 Controller、运行时替换/模拟 CUDA 接口、RDMA 数据面、Kubernetes 扩展和资源调度构成了这项能力的闭环。[S1]

因此，面向一家人形机器人公司的最佳定位是：**私有训练／仿真／长尾推理资源的效率层候选供应商和战略观察标的**，而不是当下可替代芯片软件栈、也不是应直接并购的基础设施平台。采购价值取决于它能否在公司真实的 PyTorch、NCCL、容器、网络和国产芯片组合上，用可复现实验兑现利用率、尾延迟和故障恢复；投资价值取决于它能否将“兼容 CUDA 的 GPU 池化”升级为有公开版本矩阵、可审计的多 XPU 控制面。两者都尚未由公开资料证明。[S1][S8]

本报告把公司宣传、客户测算、媒体报道和独立可核验事实分开处理。特别是“资源利用率提升 3—10 倍”“成本下降 80%”“异构算力”均不能被直接写成适用于最新 GPU、LLM 训练或全部国产芯片的普遍结论：公开可复现的性能测试停留在 Tesla P40、CUDA 9、TensorFlow 1.12 与合成数据的组合。[S1]

## 一、研究边界、主体与关键问题

### 1.1 对象与主体边界

品牌为趋动科技（VirtAITech.com），核心产品为 OrionX（猎户座）AI 算力资源池化软件，另有 Gemini AI 训练平台与“趋动云”服务入口。官网页脚展示 ICP 备案号 `京ICP备19027973号` 和公安备案号，但未直接写出法定主体。[S2][S3] 与之相对，官网仍可下载的《OrionX AI 算力资源池化解决方案技术白皮书》于 2021 年 11 月发布，第二页明确写有“版权所有 © 北京趋动科技有限公司 2021”，并称文中商标为该公司商标。这形成了品牌—产品—法律主体的强关联，故本报告将**北京趋动科技有限公司**作为研究主体。[S1]

这不是对当前工商状态的替代。白皮书能够确认 2021 年的版权与主体关联，却不自动证明 2026 年的存续状态、统一社会信用代码、实际控制人、融资后股权、知识产权归属或“趋动云”是否由同一实体经营。正式投资、并购或签约前，须以国家企业信用信息公示档案、最新章程、股东名册、软件著作权/专利清单、劳动与 IP 协议逐项复核。

### 1.2 需要回答的投资问题

1. OrionX 的“池化”究竟是虚拟化、调度，还是跨厂商 XPU 抽象？
2. 它能在机器人训练、仿真和在线推理的哪些负载上创造可量化价值，哪些环节会被网络、框架或驱动限制？
3. 标准化软件销售、趋动云租赁、合作伙伴分成三条商业线，哪一条能形成可持续软件毛利和客户黏性？
4. 从投资、战略合作、采购验证和自研四种动作看，现阶段应如何排序？

## 二、纵向分析：从 GPU 虚拟化团队到数据中心级资源池

### 2.1 早于公司成立的技术选择：解决利用率，而非再造芯片

趋动的起点不是大模型热潮中临时拼出的云平台。CEO 王鲲毕业于中国科学技术大学计算机系，曾任 Dell EMC 中国研究院院长；CTO 陈飞毕业于中科院计算所、曾任该研究院首席科学家；资深工程副总裁邹懋同样来自中科大及 Dell EMC 中国研究院。官网将三人的长期研究描述为计算机体系结构、高性能计算、GPU/FPGA 虚拟化和分布式系统。[S2] 2026 年的采访补充称，团队从 2016 年已开始做 GPU 池化，并在创业后继续打磨约三年；这属于王鲲的回顾口径，但与产品架构的技术重心相互印证。[S8]

这个来源决定了产品从一开始就不是“在 Kubernetes 外面加一个提交界面”。在 GPU 仍主要以服务器和整卡为资产单位的时期，团队把问题定义为两种浪费：一张卡没有被任务填满的空间浪费，以及任务结束后仍被长期占用的时间浪费。它选择在应用与物理 GPU 中间插入运行时和控制面：应用面对逻辑 vGPU，控制面再决定实际卡、份额和网络路径。这样做的收益是能把碎片化供给转为可调度资源；代价是兼容层必须覆盖巨大而持续变化的 CUDA 表面，以及远程数据面必须经得住训练通信和故障的考验。

### 2.2 2019：成立与第一个产品命题

公开采访称公司于 **2019 年 1 月**在北京成立，方向是 GPU 池化软件。[S8] 创业邦 2021 年融资报道也称其 2019 年成立于北京中关村高新技术园区。[S4] 当时的产品叙事集中于数据中心级 GPU 虚拟化和资源池化：不是只把单张卡切成固定比例的 vGPU，而是进一步提供远程调用、集中管理、资源调度和回收。[S1]

这是一个相当激进的边界。简单切分仍被物理服务器束缚；远程调用则把 CPU/应用服务器与 GPU 服务器解耦；资源池化再向上加入统一管理面和北向 API。趋动把这四个阶段都纳入 OrionX 的产品范围。[S1] 对企业客户而言，它承诺的是以较少的硬件覆盖更多试验、教学和推理任务；对公司本身而言，它把护城河放到了 CUDA 兼容、调度策略、数据路径和企业交付之中，而不是单一硬件渠道。

### 2.3 2020—2021：将系统软件产品化，并快速引入资本与伙伴

2021 年是公开资料最密集的一段。2 月 23 日，创业邦报道趋动完成“数千万美元级”A+ 轮，招银国际电信基金领投，高瓴创投追加；报道说这是成立两年内第四笔融资。[S4] 7 月 12 日，创业邦报道其完成“数千万美元”B 轮，由 Prosperity7 Ventures 领投，元禾重元跟投，顺为资本、高瓴创投、嘉御基金和招银国际电信基金继续跟投；同文称这是第五笔融资。[S5] 12 月 27 日的报道写其完成“数亿元人民币”B+ 轮，由普罗资本旗下国开装备基金领投，Prosperity7、元禾重元、高瓴创投跟投，并称为近三年内第六笔融资。[S6]

这些融资报道的共同点是把产品描述为企业基础软件，而不是单次集成项目。B 轮稿称其服务过交叉信息核心技术研究院、携程、中国移动咪咕、网络通信与安全紫金山实验室，并与 Dell EMC、浪潮信息、AWS、青云、Rancher、DaoCloud、科大讯飞等展开合作；同时提到 2021 年一季度中标若干项目、与西北工业大学落地部署、与图灵人工智能研究院建立联合实验室。[S5] B+ 稿还称与浪潮、容联科技共建西湖大学智算中心，并提及中信建投和北京理工大学计划部署。[S6] 这些均应视作媒体转述与公司/合作方口径：它们可以证明市场进入与交付线索，不能证明合同金额、长期续费或收入确认。

2021 年白皮书给出了产品当时已可审阅的技术快照。OrionX 将核心拆为四个组件：负责注册、发现、元数据、vGPU 调度及 REST API 的 **OrionX Controller（OC）**；发现、管理物理 GPU 并执行任务的 **OrionX Server Service（OSS）**；在应用侧提供 CUDA 运行时接口和资源申请/释放的 **OrionX Client Runtime（OCRT）**；以及面向账号、拓扑、资源、日志、告警的 **OrionX GUI（OG）**。[S1] OC 可做 2+1 冗余；管理面为 TCP/IP；数据面支持 TCP/IP、RoCE RDMA、InfiniBand RDMA 和共享内存。[S1]

更重要的是，白皮书并没有把“透明”写成抽象口号。OCRT 的路线是模拟 NVIDIA CUDA runtime，使应用在既有 CUDA 编程模型下运行；它也给出了 Kubernetes Device Plugin 和 Scheduler Extender、KVM/OpenStack、VMware、Docker/Kubernetes 的接入方式。[S1] 这种架构解释了为何趋动可在存量企业机房中销售：用户未必需要重写应用或先替换全部 IaaS 控制面。但同一事实也划出了边界——该版本兼容列表明确的是 NVIDIA GPU 与 CUDA 9.0—11.4，以及当时的 PyTorch、TensorFlow、PaddlePaddle 等版本；没有列出可验证的国产 XPU 型号、驱动和框架组合。[S1]

### 2.4 2022—2024：产品外延从池化软件延至训练平台与云入口

公开融资报道在 B+ 轮后较少连续披露，故不能据此推断这一时期的营收或融资停滞。能够确认的是，产品组合后来呈现出三层：底层 OrionX；面向项目、工作空间、镜像、代码/数据/模型版本、TensorBoard 和分布式训练的 **Gemini AI 训练平台**；以及按量提供资源的 **趋动云**。[S3][S9]

这不是三个互不相干的 SKU。Gemini 的逻辑是把底层资源池包装成开发训练工作流，降低算法团队处理环境、任务复现和协作资产的成本；趋动云则把底层虚拟化能力直接做成服务入口。官网称趋动云按分钟计费、展示最低价格和用户反馈节省比例，但这些价格、效果与用户规模应只视作营销信息，不能倒推出单位经济性或现金流。[S9]

2026 年采访把商业模式拆为三类：向自有 GPU 的企业销售软件；以趋动云出租虚拟算力；为算力租赁合作伙伴提供软件，按营收或毛利分成。采访中 CEO 称趋动云“数百张 GPU”、近 20 万注册用户、近万活跃用户及 2—5 倍超卖比。[S8] 这是解释经营逻辑的重要一手管理层口径，但尚无审计报表或独立监测可验证，因而不应用作估值的收入、活跃用户或利用率基数。

### 2.5 2025—2026：向“算力互联网”和异构叙事延伸

2025 年 12 月，公司称参与国家算力互联网服务平台接入合作；战略副总裁在会上给出“平均提升 4 倍利用率、减少 40% 能耗、降低近 60% 成本”的说法。[S10] 这些数字比 2021 年白皮书中“3—10 倍”等口径更像演讲中的综合主张，而非公开的测试报告。未披露样本、基线、硬件、任务、网络、故障率和测量期间，不能用于采购承诺。

2026 年 3 月，公司发布广东联通教育智算集群案例，称 OrionX 为该集群提供异构算力池化与调度能力。[S11] 该资料至少证明其仍在参与运营商/教育集群项目；它并不能证明趋动独立交付了“千卡集群”，也没有列出异构芯片型号、驱动版本和真实负载。3 月末，公司还称 OrionX 入选信通院“铸基计划”相关全景图和解决方案集。[S12] 这可作为外部机构名单入选的线索，不能替代产品性能或商业规模验证。

近期采访中，王鲲强调公司作为独立第三方会支持客户选用多家国产芯片，并把公司比作“电网”而不是“电厂”。[S8] 这个方向符合客户避免供应商锁定的需求，却仍是一条**待证实的产品路线**：公开的、带版本的兼容性矩阵只具体列举 NVIDIA/CUDA；官网宣称多厂商/多品牌 AI 芯片，但没有公布可审计的多 XPU 支持范围。[S1][S2] 在证据补齐以前，不能把愿景升级为已经形成的跨厂商 XPU 控制面。

## 三、技术与商业模式解剖：它交付的是“资源可见性”还是“异构抽象”？

### 3.1 OrionX 的技术链条

OrionX 的完整工作流可以概括为：OSS 发现物理 GPU，OC 汇集资源与任务状态并分配 vGPU，OCRT 在应用环境暴露兼容 CUDA 的调用接口，数据面再将应用与选定 GPU 节点连起来；GUI、REST API、Kubernetes 扩展则让运维与上层平台能够管理这一资源池。[S1] 官网当前产品页仍展示热迁移、配额、资源超分、排队优先级、跨机聚合和远程调用等能力，说明这些功能仍是其对外产品叙事的一部分，但网页本身没有给出版本、性能条件或支持矩阵。[S7] 因而它同时具有三种能力：

- **虚拟化/切分**：计算最小 1%、显存最小 1MB（该数值来自 2021 版本），适用于小模型推理、开发和教学等碎片化负载；
- **远程调用/聚合**：应用容器或 VM 可以运行在无 GPU 机器上，调用远端卡，也可将多台服务器 GPU 聚合给一个环境，支持 Horovod 或 DDP 这类分布式训练方式；
- **调度/治理**：按需申请与释放、预约/获取两种模式、队列优先级、抢占、显存超分、原生 GPU 与 OrionX GPU 双池，以及日志、监控、告警和多副本控制面。[S1]

从企业架构看，这类软件的价值并不等于“GPU 算得更快”。它主要通过让同一批硬件服务更多不同时段、不同份额的任务来提高资产周转。对开发者的无感、对管理员的全局视图、对平台的 API 接口，是同一件事的三个侧面。真正的考验却在边缘：RDMA 网络拥塞、CPU/数据位置、NCCL 拓扑、GPU 代际和驱动升级、内核/容器安全边界、故障重连、超分触发时的 QoS，都可能把理论利用率折成现实尾延迟。

### 3.2 性能和兼容性不能越过版本边界

白皮书声称本地 vGPU 损耗“几乎为零”、远程 vGPU 小于 2%，但其试验配置是双路 Xeon Gold 6132、Tesla P40、CUDA 9、cuDNN 7.4.2、TensorFlow 1.12 官方 benchmark 和 synthetic data；远程场景为 25G RDMA。[S1] 这能证明公司至少曾按明确环境测试过远程调用，却不能代表 H100/H200/B 系列、NVLink/NVSwitch、大规模 LLM 的 all-reduce、MoE、KV cache 推理或最新国产加速器。采购评估必须重跑，而非引用 2021 年的百分比。

同样，白皮书兼容清单列举的是 A100/A10/A30/A40 等 NVIDIA GPU、CUDA 9.0—11.4、旧版 Kubernetes 和早期 PyTorch/TensorFlow/PaddlePaddle。[S1] 这份清单具有双重价值：它让“以 NVIDIA CUDA 兼容为核心”成为高置信事实，也让“已广泛实现多厂商 XPU 的生产兼容”不能成立。官网今天的国产化和多品牌表述可作为尽调方向，而不是分类或交易的充分证据。[S2][S8]

### 3.3 商业化结构与可获得价值

软件销售最接近高毛利、私有化基础软件的理想形态，但销售周期、适配和现场运维也可能把它拉向项目制。趋动云有把闲置资源以更细颗粒出租的直接收入机会，却使公司承担 GPU 采购/租赁、利用率、获客、合规和服务质量风险。合作伙伴分成有利于扩张而减轻资本开支，但需要清楚的计量口径和结算审计，且可能在客户归属和渠道控制权上发生摩擦。[S8]

对投资人而言，三条线不能混算。若核心收入来自软件 license/订阅和支持，重点看续费、部署工时、毛利、版本升级与客户集中度；若趋动云占主导，则必须像审查算力租赁商一样看资产负债、卡源、机房、电力、网络、坏账和利用率；若分成占比上升，则需要审查合同期限、审计权和伙伴的真实毛利。公开资料尚不足以拆分三者的收入、毛利和现金流。

### 3.4 合作网络：关系类型不应混写

## 四、横向分析：五种“提高 GPU 利用率”的路线并不互为替代

### 4.1 所处生态位

趋动的真正同类不是所有 GPU 云，而是处在应用、调度器、虚拟化层与物理加速器之间的资源效率软件。它处在一个夹层：向下依赖 NVIDIA CUDA、驱动、网络与服务器拓扑，向上又要被 Kubernetes、训练框架和企业平台接受。这个位置的好处是可兼容存量环境，坏处是两端升级都会把适配压力压到它身上。

| 路线/代表 | 解决的主问题 | 相对 OrionX 的强项 | OrionX 的可能差异与边界 |
|---|---|---|---|
| NVIDIA vGPU / MIG | 单卡隔离、切分与硬件/驱动生态 | 厂商原生支持、硬件隔离与 CUDA 生态可验证 | OrionX 声称可远程调用、跨机聚合和数据中心级控制面；但须在同代 GPU 与具体负载上验证隔离、性能和运维差异。[S1] |
| Run:ai 等 GPU 编排平台 | Kubernetes 上的队列、配额、优先级、共享和训练工作负载治理 | 对云原生 AI 作业调度、用户/项目治理的产品化较深 | OrionX 的差异在运行时级 vGPU 与远程 GPU；其上层工作流与生态成熟度不可由公开资料直接比较。 |
| Kubernetes Device Plugin + Volcano/Kueue | 标准设备暴露、批调度、队列和配额 | 开源标准、可组合、减少专有控制面 | OrionX 已有 Device Plugin 与 Scheduler Extender，因此可能是补充层；但开源方案避免专有 runtime 依赖，企业需比较功能缺口和维护成本。[S1] |
| 国内智算 OS / 资源池平台（如九章云极等） | 多集群、云边或异构资源管理，以及训练服务 | 可能覆盖更广的运营、数据、云服务或多芯片场景 | 不能把“国内化/异构”口号当作性能结论；趋动目前公开强证据仍是 NVIDIA CUDA 池化。 |
| GPU 云/租赁商 | 卡源、供给聚合、交付和按量计费 | 可直接出售算力、承担采购与机房能力 | 趋动云虽也提供服务，但公开采访所述更具差异的部分是把软件授权给租赁伙伴并分成，而非单纯囤卡。[S8][S9] |

### 4.2 与 NVIDIA vGPU/MIG：底层隔离与跨服务器可用性之间的取舍

NVIDIA 的路线通常以特定 GPU、驱动、许可和硬件能力为中心，优势是生态一致性和更低层的隔离保证。趋动在 2021 年公开材料中选择 CUDA 兼容运行时，支持把 GPU 资源细分、远程提供给 VM/容器，也支持 native GPU 与池化 GPU 双池。[S1] 这给存量异构服务器、低利用率推理和教学负载一个明确价值：不必要求每个应用都与 GPU 同机。

然而，“软件切分更细”不是自动的优越性。显存超分会以系统内存补充逻辑显存，这对常驻但低算力的长尾推理或许有价值，却也可能让突发流量、内存压力和尾延迟变成关键约束。[S1] 对实时机器人推理，这种超分不应未经压测进入安全关键链路；对离线训练，跨机聚合还要面对网络拓扑和通信库效率。采购时需将原生 MIG/vGPU、OrionX、裸金属三组并列测量，而非只测平均吞吐。

### 4.3 与 Run:ai 和云原生编排：控制面深度不同

Run:ai、Kueue、Volcano 等路线把重点放在 AI 作业的队列、公平性、配额、抢占、gang scheduling、弹性与 Kubernetes 生态。趋动公开资料中已有任务队列、优先级、抢占、动态申请/释放，以及 Kubernetes Device Plugin 和 Scheduler Extender。[S1] 因而它不是“只有驱动”的工具，也具备 3.5 类调度与编排的直接证据。

差异在于控制面究竟管到哪里：OrionX 往下进入 vGPU 资源与远程 CUDA 调用，可能在碎片化物理资源上做得更激进；云原生调度器则更容易与既有 CRD、GitOps、可观测性、身份治理和多租户规范配合。对已经重度 Kubernetes 化的机器人研发组织，趋动不是必然替代 Volcano/Kueue，而更可能需要证明能否无侵入地与它们共存，哪些队列/抢占决策由谁拥有最终权威。

### 4.4 与“跨厂商异构调度”：当前最大机会也是证据缺口

真正的跨厂商训推调度平台应至少公开三件事：可用的芯片/驱动/框架版本矩阵；同一控制面对不同 XPU 的资源语义、拓扑、故障与性能模型；真实生产场景的隔离、迁移、训练通信和推理 QoS 证据。趋动公开材料满足“资源池、调度和集群治理”的第一层能力，也表达支持国产生态和多厂商芯片的方向。[S2][S8][S11] 但尚未公开前两项足以复核的材料。

因此，此刻把趋动与“多厂商 XPU 已成熟抽象”的公司并排估值会失真。它的机会是客户出于供应安全而需要独立第三方控制层；它的危险是各 XPU 的编译器、运行时、通信库和框架后端差异足以让“统一接口”停在销售叙事。只有在硬件、软件和负载矩阵中持续交付，才可能把这个叙事变成壁垒。

### 4.5 用户视角：选择它的理由与可能的槽点

从公开产品与客户表述推断，趋动的典型买方是已购置 GPU、但资源分散在多个机房/服务器、算力需求有潮汐而又不愿重写应用的企业、院校和运营商。它们购买的不是单卡峰值，而是“资源突然可见、任务可以排队、碎片可被回收”的运营体验。[S1][S5] 这解释了金融、教育、运营商和研究机构在其公开案例中占比较高。

真实用户口碑和独立社区评测在本轮公开检索中不足，不能伪造为“用户评价”。相应的潜在摩擦可以从架构而非传闻推导：专有 OCRT 带来版本与安全审查成本；远程 GPU 使网络、数据位置和通信库变得更重要；细粒度切分/超分需要明确隔离和 QoS 边界；企业现场部署还要面对 license、升级回滚、日志留存和故障归因。[S1] 这些都是 POC 必测项，不是对产品已经失败的判断。

## 五、横纵交汇：早期的 CUDA 选择塑造了今天的优势，也限定了扩张速度

趋动最值得重视的历史选择，是在 GPU 极其稀缺之前就押注“利用率”而非“算力供给”。这让它比后来的 GPU 租赁商多了一层软件价值，也比只做训练门户的产品更深入地进入运行时和数据路径。团队的虚拟化/系统背景使 OC、OSS、OCRT 与 RDMA 数据面形成了完整叙事；2021 年连续融资和随后在教育、运营商等场景出现的项目线索说明市场愿意为这一叙事付费尝试。[S1][S4][S5][S11]

但同一选择也形成了路径依赖：OCRT 以 CUDA 兼容为中心，白皮书兼容矩阵也以 NVIDIA/CUDA 为中心。[S1] 当产业从“GPU 供不应求”进入“多种国产芯片并存、LLM 通信密集、推理追求尾延迟”的阶段，业务不再只要求把一张卡分给多个人，而要管理不同硬件的能力、通信、框架、模型和失败模式。公司可以从独立第三方位置受益，也必须为每个新 XPU 支付更高的适配、验证和支持成本。

### 5.1 三种情景

**最可能情景（概率最高）——成为国内企业 GPU 效率层的稳定供应商。** OrionX 继续以 NVIDIA GPU、私有化部署、教育/金融/运营商和合作伙伴云为主，Gemini 与趋动云提高入口和粘性。价值来自减少闲置、改善运维与提高设备服务人数，而非颠覆芯片生态。触发依据是既有 CUDA 架构、历年项目线索及管理层披露的三条商业线。[S1][S8]

**乐观情景——把运行时资产升级为经验证的多 XPU 控制面。** 公司公布并持续维护国产 GPU/NPU 与主流框架、通信库、容器平台的版本矩阵；在真实混合集群中证明统一调度、隔离、可观测性和 QoS；再把与运营商/算力互联网的合作转成可复用产品。届时“独立第三方”可从销售话术变成供应安全的基础设施位置。必要条件不是更多“异构”新闻，而是可审计的兼容与性能证据。

**危险情景——运行时兼容债务与云价格战同时发生。** CUDA/驱动、框架和硬件快速更迭令适配成本高于 license 收入；大型云、芯片厂商或开源 Kubernetes 堆栈吞掉基础调度需求；趋动云又在卡源和价格上与更大租赁商竞争。届时公司可能保有一批定制交付，却难以形成可扩张的软件毛利。预警指标包括版本滞后、现场定制人天上升、支持费用增加、云业务毛利下滑与客户集中度升高。

## 六、面向人形机器人公司的动作建议

### 6.1 采购：可做受控 POC，不做生产承诺

**建议动作：P0 技术验证，目标为 6—8 周的隔离环境 POC。** 选择三类真实负载：多模态/世界模型离线训练（含 DDP/NCCL）；仿真或数据处理的潮汐批任务；长尾视觉/语言模型推理。分别在裸金属、现有 Kubernetes 调度方案、OrionX 三组环境测量 GPU SM/显存利用率、排队时长、吞吐、p95/p99 延迟、训练收敛、故障恢复、网络流量、运维人时和每有效 GPU 小时成本。不要用厂商基准替代这一测试。

POC 的硬性退出条件应包括：关键 PyTorch/CUDA/NCCL 版本不兼容；远程或切分模式在目标任务上使收敛/尾延迟明显恶化；故障恢复、审计、隔离和访问控制不满足内部要求；不能与现有 Kueue/Volcano/平台权限模型清晰分工。通过后再考虑在开发、仿真和非安全关键推理池扩展；实时控制链路、生产机器人在线安全决策仍优先原生、可预测的硬件路径。

### 6.2 投资：观察优先于估值谈判

**建议动作：战略观察名单，可用 POC 结果换取优先尽调权；暂不以“跨 XPU 平台”溢价立项。** 看好点是团队的系统软件基因、产品在资源池化上的明确技术闭环、以及企业客户对设备效率和供应独立性的真实痛点。保留意见是财务、客户留存、股权、当前产品支持矩阵和多 XPU 生产能力均未公开证实。

投资前的 P1 清单：

1. 获取截至尽调日的工商、股权、期权池、历史融资文件与全部 IP 归属，确认北京趋动科技有限公司、品牌、OrionX、Gemini 和趋动云的权利边界；
2. 按软件销售、云服务、渠道分成拆分最近 24 个月收入、毛利、续费、部署/支持成本、应收和客户集中度；
3. 对 5—10 个客户做独立访谈，核验部署规模、实际活跃率、故障、续费和替代方案，不以新闻名单代替客户验证；
4. 获取当前 XPU、驱动、CUDA/框架/NCCL/Kubernetes 兼容矩阵、自动化回归报告、漏洞修复和升级策略；
5. 对趋动云审查 GPU 资产/租赁承诺、机房与网络合同、利用率、超卖风控、计费争议和数据安全责任。

### 6.3 并购：当前不建议启动控制权交易

**建议动作：不启动并购报价；可在 POC 成功且满足以下触发条件后重评。** 第一，产品在本公司真实机器人负载上产生可持续的成本/交付优势；第二，核心运行时、调度与客户合同的知识产权完整可转让；第三，多 XPU 能力经公开或私有测试验证，且关键团队留任和开源/第三方许可不存在断裂；第四，交易后能保留其对外生态的中立性。过早并购会把一个依赖多家芯片、云和渠道伙伴的独立控制层变成单一客户的内部工具，反而削弱其外部价值。

### 6.4 自研边界

本公司应自研的是与机器人任务强绑定的资源策略：仿真优先级、数据闭环 SLA、模型版本与数据集之间的算力归因、硬件在环与安全控制资源隔离。通用 GPU 虚拟化、CUDA 兼容 runtime、RDMA 数据面和企业控制面没有必要在短期重复建设，除非 POC 表明外部产品无法满足安全、国产芯片或性能要求。自研芯片的判断更不应建立在“有池化软件就能抹平生态差异”之上：软件可以改善资源周转，不能自动补齐编译器、通信、算子、驱动和开发者生态。

## 九、产业链分类复核（报告末尾结论）

**主分类：`3.5 调度与编排软件`（高置信）。** OrionX 的 OC 明确承担 vGPU 调度、服务发现、资源申请/释放，产品还公开列出队列、优先级、抢占、按需伸缩、Kubernetes Scheduler Extender 与 REST API。[S1] 这些是直接、可追溯的调度和编排证据，且最贴近其价值创造：把分散 GPU 按任务和策略分配出去。

**次分类：`3.6 集群管理软件`（中高置信）。** 产品具备资源发现、全局 GPU 资源池、组件拓扑、状态同步、2+1 控制器高可用、GUI、日志、监控和告警能力。[S1] 它不是单纯作业调度器；但商业核心仍是调度/池化，故 `3.6` 应列为次要分类。

**不列入正式次分类 `4.1 跨厂商训推算力调度平台`。** 官网和管理层虽主张多厂商/国产芯片支持，2021 公开兼容性清单却只具体列 NVIDIA GPU/CUDA，缺少不同 XPU 的驱动、框架、通信库和生产验证矩阵。[S1][S2][S8] “异构”不能被自动解释为已完成跨厂商 XPU 统一调度。

**不列入正式次分类 `4.4 多厂商算力池`。** OrionX 已被强证据证明是跨服务器的 GPU 资源池，但“多厂商算力池”要求可核验地纳管多个芯片厂商，而非多型号 NVIDIA GPU、生态合作或路线图。当前证据未满足这一门槛。[S1][S11]

### 方法说明

本报告按横纵分析法，将团队与产品的历时演进同 2026 年资源池、云原生编排、厂商原生虚拟化及异构调度竞争格局交叉分析；结论以可回溯证据为前提，未被证实的商业和技术能力均保留为尽调问题。
