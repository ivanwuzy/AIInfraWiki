# VLA/WAM 训练负载特征与现有 Infra 瓶颈分析

> 研究范围：基于 pi0、Cosmos WFM 等公开模型训练的学术论文、博客和技术报告，以及本知识库产业链证据
> 研究截止日：2026-08-14
> 用途：为训练芯片孵化方向提供负载特征层面的瓶颈验证，更新 [[segments/6.5-视觉语言动作模型]] 和 [[segments/6.6-动作世界模型]] 中的技术判断

## 核心合成结论

### 一句话总结

**VLA/WAM 训练负载对现有 GPU/TPU 平台的核心瓶颈不在峰值算力（FLOPs），而在内存带宽、长序列注意力、多模态数据管线、大规模并行效率和训练稳定性——这些瓶颈共同指向一个更具体的芯片优化方向，而非通用训练 ASIC 的"替代性"论证。**

### 关键发现

1. **VLA 训练并非计算密集型**：pi0 3.3B 模型在 700k 步预训练的计算量远小于同等规模 LLM（Llama 3 8B 训练 2T tokens），瓶颈在于数据采集成本和多模态融合，而非 FLOPs 供给不足
2. **WAM 训练才是真正的计算密集型**：Cosmos 14B 世界模型需要 10,000 H100 GPU 训练 3 个月，其计算量远超大多数 LLM，但瓶颈集中在长序列注意力和视频编解码
3. **现有 GPU 的主要瓶颈是序列长度和 HBM 带宽**：56K token 序列长度下，标准注意力复杂度 O(n²) 使得计算/内存比远低于 LLM 训练，HBM 带宽成为瓶颈
4. **视频编解码是未充分加速的瓶颈**：20M 小时视频数据的预处理需要 GPU 加速编解码（NVDEC/NVENC），CPU 管道无法胜任
5. **训练稳定性是隐藏瓶颈**：Cosmos 团队花费大量工程努力解决注意力 logit 增长、loss spikes、图像-视频分布不匹配等问题，这些在芯片设计中无法直接解决

## 一、VLA 训练负载瓶颈分析

### 1.1 计算负载画像

#### 1.1.1 pi0 规模估算

| 维度 | pi0 值 | 与 LLM 对比 |
|------|-------|-----------|
| 参数量 | 3.3B（3B VLM + 300M action expert） | 小于 Llama 3 8B |
| 训练步数 | 700k 步 | 约 Llama 3 的 1/10 |
| 数据量 | 10K+ 小时机器人数据 | 远小于文本 token 量 |
| 推理计算 | 73ms/step（RTX 4090） | 比纯文本推理重 5-10 倍 |
| 训练计算 | 未公开 | 估算为 LLM 同参数量级的 1/3-1/2 |

**关键推断**：VLA 训练在当前 GPU 上 FLOPs 利用率的主要瓶颈不是计算单元不够，而是多模态数据融合和长序列带来的内存/带宽压力。

#### 1.1.2 计算热点拆解

VLA 的前向/反向传播可分为以下热点区域：

| 热点 | 占比估算 | 计算类型 | 瓶颈类型 |
|------|---------|---------|---------|
| 多视角 ViT 编码 | 20-30% | 矩阵乘法 + 注意力 | 可并行，但多视角增加显存 |
| VLM 语言骨干 | 40-50% | 注意力 + FFN | 类 LLM 计算，可复用现有优化 |
| Action expert flow matching | 10-15% | 多步 FFN + 注意力 | 多步推理增加计算量，但算子简单 |
| 多模态融合 | 5-10% | 跨模态注意力 + 对齐 | 不规则访存模式，非标准 GEMM |
| 数据预处理 | 5-10% | 图像解码、resize、增强 | CPU 瓶颈，GPU 利用率低 |

### 1.2 内存瓶颈

#### 1.2.1 显存需求分析

VLA 训练显存需求远高于同参数量 LLM：

| 组件 | 显存需求（3.3B 模型估算） | 说明 |
|------|------------------------|------|
| 模型参数 + 梯度 | ~26 GB（FP16 + FP32 副本） | 与 LLM 相当 |
| Optimizer state | ~40 GB（AdamW） | 与 LLM 相当 |
| 激活值（多帧） | 30-60 GB | 比 LLM 高 3-5 倍 |
| 图像编码器中间结果 | 10-20 GB | 多视角独立编码 |
| 输入数据 | 5-10 GB | 多帧/多视角图像 |
| **总计** | **111-156 GB** | H100 80GB 需 2-4 卡 TP |

#### 1.2.2 HBM 带宽压力

- 长序列注意力（10K-50K tokens）的 FLOPs/Byte 比远低于短序列
- 激活值 checkpointing 会增加 33% 额外计算量来换取显存
- 多视角编码使注意力计算量按视角数线性增长

### 1.3 通信瓶颈

- 多帧序列需要序列并行，增加跨节点通信量
- 图像编码器与 VLM 骨干的计算量不均，流水线并行效率低
- 小批量时通信比计算占比高，大批量时显存不足

## 二、WAM 训练负载瓶颈分析

### 2.1 计算规模画像

#### 2.1.1 Cosmos 级规模

| 维度 | Cosmos 值 | 说明 |
|------|----------|------|
| 集群规模 | 10,000 H100 GPU | 约 10-15 个标准 SuperPod |
| 训练时长 | 3 个月 | 持续训练时间极长 |
| 模型参数 | 7B-14B | 中等规模，但序列极长 |
| 序列长度 | 10K-56K tokens | 远超 LLM 典型值 |
| 数据量 | 20M 小时 → 10^8 片段 | 数据管线和 I/O 是主要挑战 |
| 分词器 | 77-105M 参数 | 额外的前向/反向计算 |

#### 2.1.2 计算热点拆解

| 热点 | 占比估算 | 计算类型 | 瓶颈类型 |
|------|---------|---------|---------|
| 3D 注意力 | 50-60% | 长序列 QKV 注意力 | **序列长度导致 O(n²) 复杂度**，远超 LLM |
| FFN 层 | 20-25% | 矩阵乘法 | 类 LLM，可优化 |
| AdaLN/条件 | 5-10% | 层归一化 + 缩放 | 参数开销大（AdaLN-LoRA 解决） |
| 视频分词器 | 5-10% | 3D 卷积 + 注意力 | 额外的编解码计算 |
| 文本编码 | 5-10% | T5-XXL 11B 编码器 | 额外的推理开销 |

### 2.2 内存瓶颈

#### 2.2.1 显存需求分析

| 组件 | 显存需求（14B 模型估算） | 说明 |
|------|------------------------|------|
| 模型参数 + 梯度 | ~112 GB | 14B FP16 + FP32 |
| Optimizer state | ~168 GB | AdamW 三个状态 |
| 激活值（56K 序列） | 100-200 GB | 长序列注意力激活值巨大 |
| 分词器 | ~1 GB | 相对较小 |
| 输入数据 | 10-20 GB | 多帧视频数据 |
| **总计** | **391-501 GB** | 需 8-16 卡 TP/CP |

Cosmos 使用 FSDP 64 + CP 8 的配置，说明单卡显存不足以容纳完整模型和长序列激活值。

#### 2.2.2 HBM 带宽瓶颈

**长序列注意力是 WAM 训练的核心瓶颈**：

- 56K token 序列 → 注意力矩阵大小 56K × 56K = 3.1B 元素
- 单次注意力前向传播需约 3.1B × 2 bytes × num_heads 的内存访问
- 以 H100 的 3.35 TB/s HBM 带宽计算，仅注意力计算的内存访问时间就占显著比例
- 相比 LLM 4K 序列（16M 注意力矩阵），WAM 的注意力 O(n²) 膨胀超过 2 个数量级

### 2.3 通信瓶颈

| 类型 | 配置 | 通信量 | 瓶颈 |
|------|------|--------|------|
| FSDP all-gather | 64 路 FSDP | 14B × 2 bytes = 28GB / 步 | AllReduce 带宽需求极高 |
| 上下文并行 | 8 路 CP | 跨节点注意力通信 | 长序列跨节点注意力延迟 |
| 张量并行 | 8 路 TP（可选） | 每层通信 | 增加集群内部带宽需求 |
| 数据加载 | 10^8 视频片段 | 多 TB/epoch | 存储和网络 I/O 瓶颈 |

### 2.4 数据管线瓶颈

Cosmos 论文明确指出了数据管线的多个瓶颈：

1. **视频编解码异构性**：多种编码格式，统一转码为 h264_nvenc 是巨大工程
2. **NVDEC/NVENC 利用率**：ffmpeg 无法充分利用 GPU 硬件编解码器，需替换为 PyNvideoCodec（6.5× 提升）
3. **标注 LLM 开销**：VILA 标注需要 FP8 量化 TensorRT-LLM 引擎（10× 加速）才能跟上训练速度
4. **去重计算**：k-means k=10,000 聚类 + 25 亿帧对的大规模去重需要 GPU 加速

## 三、跨 VLA/WAM 的共享瓶颈与差异化瓶颈

### 3.1 共享瓶颈

| 瓶颈 | VLA 影响 | WAM 影响 | 紧急性 |
|------|---------|---------|-------|
| 长序列注意力 O(n²) | 高（10K-50K tokens） | 极高（10K-56K tokens） | P0 |
| HBM 带宽 | 高（多帧激活值） | 极高（注意力矩阵） | P0 |
| 多模态数据管线 | 高（多视角视频 + 动作） | 高（20M 小时视频） | P0 |
| 训练稳定性 | 中（多任务平衡） | 高（loss spikes, 收敛） | P1 |
| Checkpoint I/O | 中（3.3B） | 高（7B-14B） | P1 |
| FSDP 通信 | 中（3.3B） | 高（7B-14B + 长序列） | P1 |

### 3.2 差异化瓶颈

| 瓶颈 | VLA | WAM |
|------|-----|-----|
| 推理延迟要求 | 实时 50Hz，需 <20ms | 可批量/离线预测 |
| 实时推理优化 | 消费级 GPU 即可（RTX 4090） | 不可部署在边缘 |
| 数据采集 | 10K+ 小时机器人操作数据 | 20M 小时互联网视频 |
| 模型收敛 | 700k 步 | 3 个月 × 10K GPU |
| 动作建模 | Flow matching 多步推理 | 扩散/自回归生成 |
| 视觉编码 | 多视角独立编码 | 时空联合编码 |

### 3.3 对训练芯片的启示

#### 可直接优化的方向

1. **长序列注意力加速器**：HBM 带宽和注意力计算是最大瓶颈，专用注意力加速单元（如 Flash Attention 的硬件化）有明确价值
2. **视频编解码硬件加速**：NVDEC/NVENC 已经是基础需求，但编解码管线的端到端优化（GPU 直接访问、减少 CPU 中转）还有空间
3. **高 HBM 容量**：WAM 训练需要 400-500GB 总显存，提高单卡 HBM 容量（如 H100 80GB → 下一代 144GB+）直接减少并行复杂度
4. **高 HBM 带宽**：注意力矩阵的带宽敏感型访问模式，HBM3/HBM4 带宽提升直接转化为训练吞吐提升

#### 需谨慎评估的方向

1. **专用 VLA 训练 ASIC**：VLA 训练的计算量不够大，不足以支撑专用 ASIC 的 NRE 成本
2. **替代 CUDA 的通用训练芯片**：VLA/WAM 的核心瓶颈是序列长度和带宽，不是缺少特定算子
3. **"物理 AI 专用"芯片**：在 VLA/WAM 架构收敛前，专用硬件可能过早固化

#### 条件性优化方向

1. **多模态融合加速**：如果本公司 workload 确定多模态融合是稳定瓶颈，可在芯片中加入跨模态注意力加速
2. **Flow matching/diffusion 加速**：连续动作生成的多步推理在芯片级优化
3. **稀疏计算加速**：点云、触觉等稀疏传感器数据处理需要非标准 GEMM 加速

## 四、对现有 GPU 平台的瓶颈验证

### 4.1 NVIDIA H100/B200

| 能力 | 对 VLA 的适配 | 对 WAM 的适配 | 瓶颈 |
|------|-------------|-------------|------|
| FP8/BF16 Tensor Core | 适配良好 | 适配良好 | 利用率受限于序列长度导致的非矩阵计算 |
| 80GB/192GB HBM | VLA 勉强够（2-4 TP） | WAM 严重不足（8-16 TP） | HBM 容量是首要瓶颈 |
| 3.35 TB/s HBM 带宽 | 注意力瓶颈明显 | 极度瓶颈 | 56K 序列注意力带宽需求远超供给 |
| NVLink 通信 | 中规模适配 | 大规模通信是瓶颈 | 10K GPU 场景下通信拓扑优化复杂 |
| NVDEC/NVENC | 基础可用 | 需替换为 PyNvideoCodec | 硬件编解码器利用率不足 |

### 4.2 国产 GPU/NPU

| 能力 | 对 VLA/WAM 适配 | 主要差距 |
|------|---------------|---------|
| FP8/BF16 Tensor Core | 多数不支持 | 长序列训练需要 FP8 才能降低显存 |
| HBM 容量 | 多数低于 80GB | 对 WAM 训练构成严重限制 |
| HBM 带宽 | 低于 NVIDIA 的 50-70% | 对长序列注意力训练影响更大 |
| 注意力加速 | 大部分无专用加速 | 长序列注意力是 VLA/WAM 核心瓶颈 |
| 视频编解码 | 大部分无或弱 | WAM 数据管线必需 |
| 序列并行/CP | 软件栈支持不足 | 长序列训练效率低 |
| 通信库 | 带宽和扩展性不足 | 大规模集群训练受限 |
| 训练稳定性 | 缺少大规模验证 | 收敛性和数值一致性未验证 |

### 4.3 谷歌 TPU v5p

| 能力 | 对 WAM 适配 | 优势 |
|------|-----------|------|
| 高带宽内存 | HBM 带宽高 | 有利长序列注意力 |
| 大容量 HBM | 95GB/卡 | 优于 H100 80GB |
| Pallas 自定义 kernel | 可编写注意力 kernel | 比 NVIDIA 更灵活 |
| 大规模集群 | 4096-8960 卡已验证 | 可扩展 |
| 受限的软件栈 | 非 PyTorch 原生 | 迁移成本高 |

## 五、对训练芯片孵化的具体建议

### 5.1 验证现有负载的优先动作

根据本分析，**训练芯片孵化方向**中的"阶段 0：负载审计与团队成核"应优先验证以下问题：

1. **本公司 VLA/WAM 训练的序列长度分布**：是 10K、50K 还是 100K+？这直接决定注意力瓶颈的严重程度
2. **多视角视频帧数**：4 相机、8 相机还是更多？视觉编码器计算量按视角数线性增长
3. **数据预处理瓶颈**：视频编解码、标注、增强中 CPU 占比多少？GPU 利用率如何？
4. **通信 vs 计算占比**：在现有集群上，FSDP/TP/CP 的通信时间是计算时间的多少？
5. **训练稳定性问题**：是否存在 loss spikes、收敛慢、梯度冲突等问题？

### 5.2 芯片设计的具体优化方向

#### 高优先级（P0，可不依赖特定 workload 判断）

1. **注意力加速**：支持 Flash Attention 级优化的硬件注意力单元，特别是对长序列的近似注意力（如 sliding window、稀疏注意力）的硬件支持
2. **高 HBM 容量**：单卡 HBM 容量应 >= 144GB（H200 级），最好达到 192-288GB，减少 WAM 训练的并行维度
3. **高 HBM 带宽**：HBM3/HBM4 带宽提升是 VLA/WAM 训练性能提升的直接来源
4. **视频编解码流水线**：GPU 内直接访问视频编解码硬件，减少 CPU 中转和内存拷贝

#### 中优先级（P1，需 workload 验证）

1. **多模态融合加速**：跨模态注意力、异步传感器对齐的硬件支持
2. **稀疏/不规则计算加速**：点云、触觉等稀疏传感器数据的处理
3. **序列并行优化**：跨节点注意力通信的硬件级支持（如 RDMA 直接访问 HBM）
4. **灵活精度支持**：同一模型中不同模块（视觉编码器、VLM、action expert）使用不同精度

#### 低优先级（P2，架构收敛后再评估）

1. **动作生成专用加速**：Flow matching/diffusion 多步推理的硬件加速
2. **物理仿真引擎集成**：GPU 内嵌物理引擎（如刚体动力学、碰撞检测）
3. **3D 渲染加速**：显式 3D 路线的光栅化/光线追踪硬件

### 5.3 与现有合成结论的衔接

**本分析与 [[训练芯片孵化证据与人才方向]] 的衔接**：

1. **支持"软件先行"定位**：VLA/WAM 训练的核心瓶颈（序列长度、带宽、数据管线）大部分可以通过软件优化（Flash Attention、序列并行、高效编解码）缓解，不需要立即造芯
2. **细化"芯片瓶颈"假设**：原报告指出"VLA/WAM 负载特征尚未形成可承重证据"，本分析初步建立了基于 pi0 和 Cosmos 的负载特征，但需要本公司 workload 验证
3. **修正"DPU/VPU 需求"假设**：专题报告中的 DPU/VPU 需求在本分析中可进一步细化为视频编解码加速器和稀疏计算加速器，而非通用数据处理单元
4. **支持"阶段门"控制**：在阶段 0 确认序列长度、带宽利用率和数据管线瓶颈后，再决定阶段 2 的硬件优化方向

### 5.4 关键开放问题

1. **本公司 VLA/WAM 模型规模**：是 3B 级（如 pi0）、7B 级（如 OpenVLA）还是更大？直接影响计算需求
2. **训练数据规模**：10K 小时 vs 100K 小时 vs 百万小时级？直接影响数据管线瓶颈
3. **仿真 vs 真实数据比例**：仿真数据量越大，sim-to-real 计算需求越高
4. **RL 训练占比**：RL rollout 的计算量可能远超模型训练本身
5. **推理部署场景**：端侧推理 vs 云端推理，对芯片的实时性要求不同
