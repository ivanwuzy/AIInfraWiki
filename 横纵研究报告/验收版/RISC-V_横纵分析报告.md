## 一、一句话定义与结论先行

**RISC-V 是一套可自由采用、由 RISC-V International 维护的开放指令集架构（ISA）及其扩展规范；它提供“设计处理器的语言”，不提供一颗现成的 CPU，更不等同于 AI 加速器、机器人控制器或可直接采购的软件平台。**【S1】【S2】

这一区分决定了本报告的结论。若把 RISC-V 当作“国产替代 CPU”、或把一颗采用 RISC-V 控制核的 NPU 当作“RISC-V AI 芯片”，很容易把技术叙事误当为供货、性能和软件能力。对一家人形机器人公司而言，RISC-V 不是训练集群或 VLA 推理的捷径；它更像一张**可在自研 SoC、传感器节点、关节控制、加速器控制面和安全隔离设计中使用的长期选择权**。

我的判断是：

| 决策问题 | 结论 | 原因与边界 |
|---|---|---|
| 是否把 RISC-V 列为独立投资赛道？ | **否。** | ISA 是非营利组织维护的开放标准，不是可直接投资的单一商业主体；价值捕获发生在 CPU/IP、SoC、工具链、验证、安全 IP、软件与垂直交付。 |
| 是否把它当作机器人主算力／训练算力的短期替代？ | **否。** | 训练与高端推理的瓶颈是加速器、HBM、互联、编译器、通信库与框架生态；ISA 开放并不自动补齐这些层。HPC 研究仍把“需要优先解决的问题”作为推动采用的前提。【S5】 |
| 是否在新一代机器人 SoC 中保留 RISC-V 选项？ | **是，分层采用。** | 低功耗 MCU、实时协处理器、传感器／执行器网关、NPU/DPU 的控制面最契合其可定制性；但功能安全、实时确定性、驱动和生命周期责任需由完整 SoC 与供应商承担。 |
| 是否立即自研通用高性能 RISC-V 应用处理器？ | **不建议。** | 自由 ISA 只免除了 ISA 使用权，不能免除微架构、验证、物理实现、软件适配、量产、客户支持与安全认证的成本。 |
| 投资／并购该看什么？ | **看“可验证的系统能力”，不看“使用 RISC-V”标签。** | 优先筛选已量产或有可复现实证的实时控制、安全岛、验证／测试、编译与部署、机器人边缘 SoC 团队；警惕只出售 RTL 或“自主可控”故事、却没有工具链和客户闭环的标的。 |

这份结论既不是对 RISC-V 的唱衰，也不是为开放生态喝彩。它是在一个更具体的问题下得出的：如果机器人公司要把钱、团队和验证周期投在能降低 BOM、缩短开发、提高交付确定性或减少供应依赖的地方，RISC-V 的价值要由**它替代了哪一颗控制核、减少了哪一种 IP／供应约束、以及增加了多少软件与验证成本**来计算。

## 二、纵向分析：从伯克利实验到开放标准基础设施

### 1. 2010—2014：它一开始不是一门“开放芯片生意”

RISC-V 的开端有一个很容易被后来的商业宣传掩盖的细节：它先是研究工具，后才成为产业标准。RISC-V International 的历史页面称，Krste Asanović 与研究生 Yunsup Lee、Andrew Waterman 在 **2010 年 5 月**于 UC Berkeley Parallel Computing Laboratory 启动该指令集，David Patterson 当时担任该实验室主任。【S1】

这个起点解释了 RISC-V 的原始气质。研究者要探索处理器、并行计算、编译器和系统时，需要一套足够干净、可实现、可修改且不用逐次谈许可的 ISA。一个现成的商业 ISA 即使功能强，也会把研究限制在既定授权、实现和文档边界内。RISC-V 的第一性目标因而不是“做一颗比某某更快的芯片”，而是让硬件、系统软件和教学研究可以围绕一个公开接口长期累积。

这也解释了它今天最常被误解的地方。ISA 是软件看到的寄存器、指令、异常、特权级和内存语义的契约；它并不规定芯片的流水线深度、乱序执行、缓存一致性、片上互联、DDR/HBM 控制器、NPU MAC 阵列、功耗管理或车规可靠性。两个都叫 RISC-V 的芯片，可以一个是几十毫瓦的 MCU，另一个是 Linux 主机核；它们共享的是程序二进制层面的约定，不是性能、软件包或交付质量。

2014 年的《Instruction Sets Should Be Free: The Case For RISC-V》以及 2011 年的手册，成为该路线从实验室工件转向公开论证的早期节点；RISC-V International 在其历史页中将它们作为发展脉络的一部分列出。【S1】这类论证的核心并非“免费必然更先进”，而是把 ISA 作为长期、可移植的公共接口。对后来担心单一授权主体、出口限制或架构锁定的公司来说，这个命题格外有吸引力。

### 2. 2015—2018：从项目变成治理组织，开放才开始有了约束

2015 年的第一次 RISC-V Workshop 和随后成立的 RISC-V Foundation，是第二个更重要的转折。官方历史页记载，该基金会在当年以 **36 个创始成员**启动。【S1】从此，RISC-V 不再只是某个实验室发布的一套文档，而开始处理标准文本、商标、成员协作、扩展命名和兼容性这类不那么“性感”、却决定生态能否成立的事务。

开放不是“谁都能随便改”。一个 ISA 若没有稳定的共同部分，软件会被碎片化实现拖垮；一个 ISA 若不允许扩展，又会失去做领域优化的优势。RISC-V 的答案是将基础 ISA 和被批准的扩展交给组织化的规范流程，将厂商差异更多留在实现和受约束的扩展空间。RISC-V International 现在仍强调：其成员共同开发、批准和维护规范；已批准的标准保持稳定，原文本不再直接修改，必要改动要通过后续扩展处理，且已批准扩展不再修订。【S2】

这套安排是 RISC-V 的强项，也是它的长期工程负债。

强项在于，芯片公司可以在不受单一 ISA 授权人控制的前提下构建产品，软件作者也可以围绕长期稳定的基线做编译器、内核和运行时。负债在于，真正能让应用无痛运行的，不是“有 RISC-V”四个字，而是具体芯片是否实现了相同扩展、ABI、启动固件、IOMMU、虚拟化和外设平台；越强调可扩展，越需要 profile、测试和发布纪律把差异收束回来。

对机器人 SoC 而言，这个矛盾尤其尖锐。电机控制、相机、EtherCAT/CAN、实时调度、安全岛和加速器 DMA 都会牵出大量芯片外的接口。允许为这些场景做定制，是 RISC-V 的好处；若每一家 SoC 都留下自己的指令、固件和 SDK 岔路，机器人软件团队得到的就不是自由，而是一组需要终身维护的端口。

### 3. 2018—2020：Linux Foundation 支持与瑞士注册，把“可持续性”摆到台面上

2018 年，RISC-V Foundation 宣布与 Linux Foundation 合作，后者提供运营、技术和战略支持，包括会员管理、基础设施工具、社区、法律和开放标准服务。【S1】这不是一个处理器性能事件，却是生态演进的关键。大规模标准从来不只靠 ISA 文档活着：会议、代码托管、法律治理、知识产权政策、认证讨论、培训和成员协调都是隐形基础设施。

2020 年，组织注册为瑞士的 RISC-V International Association。官方说明将此描述为对社区长期战略风险的管理，而非针对单一国家、公司、政府或事件的反应。【S1】从投资视角看，这一步并没有让任何芯片天然规避出口、代工或 EDA 风险；RISC-V 自己也不经营商业产品。它解决的是另一层风险：**标准接口不被某一个商业许可方单边控制，且参与者能预期该共同接口会持续存在。**

这个差别值得把话说重一点。ISA 开放降低的是“使用该指令集本身”的制度性门槛；机器人整机仍然要面对先进工艺、物理 IP、EDA、DDR/HBM、封测、板级器件、固件签名、供应质量和海外软件依赖。把 ISA 开放直接推导成“芯片完全自主可控”，是把供应链问题缩写成了一个口号。

### 4. 2020—2023：扩展越来越多，生态的难题从“有没有”变成“如何不散”

RISC-V 进入产业视野后，标准本身从最初的基础整数指令集，逐步形成了特权架构、向量、虚拟化、调试、安全相关扩展与 profile 等更宽的组合。对 AI 与机器人有意义的并不是每一项扩展的名称，而是三件事：

1. 应用处理器能否形成足够一致的 64 位 Linux 用户态和 ABI；
2. 编译器、内核、容器、调试器和性能分析工具是否能识别硬件特性；
3. 需要实时、安全或功耗优化的 SoC，能否将专有硬件差异控制在清晰的驱动和运行时边界内。

Linux 内核已经维护专门的 RISC-V 架构文档，覆盖启动要求、ACPI、虚拟内存、硬件探测、用户 ABI、向量扩展、间接控制转移与 shadow stack 等主题。【S4】这说明主线系统软件不再把 RISC-V 当作一次性的实验端口。不过，内核目录的存在只证明上游接口在维护；它不能替一颗具体芯片证明摄像头、PCIe、NPU、EtherCAT、功耗管理、容器镜像或长期安全更新已经可用于机器人量产。

为了收束这种差异，profile 的作用变得越来越大。可以把 profile 理解为“某类机器至少要实现哪些 ISA／扩展特征”的共同底盘。RISC-V 的 profile 理由文档直言，扩展批准只能保证“实现某扩展时的规格一致”，不能保证一组扩展会同时存在；对二进制软件市场，RVA profile 的首要目的正是让软件依赖某一代实现中存在的一组特性，并警告缺少主动对齐会令 RISC-V 在此类市场失去竞争力。【S7】RVA23 进一步将 64 位应用处理器对齐为更大的保证集合，并把此前在 RVA22 中可选的 V 向量扩展列为强制项。【S7】

这不让性能相同，却让发行版、编译器和应用不必对每个 SoC 猜测指令集合。对未来高性能 RISC-V Linux 设备，profile 的成熟度是从“能启动”走向“能作为产品维护”的必要条件；对小型实时 MCU，则更需要看 RTOS、驱动、调试和安全机制，而不能生搬硬套 Linux 的评价尺子。更直观的反证来自 QEMU 的 RISC-V 文档：它解释说 RISC-V SoC 的设备组合差异显著，通常一个机器可启动的操作系统或固件镜像在另一台机器上根本无法启动。【S7】这正是机器人采购时必须查 BSP、设备树、启动链与外设驱动，而不能只看 ISA 标识的原因。

### 5. 2023—至今：RISE 把软件问题公开化，恰恰说明它还不是自动解决的

RISE（RISC-V Software Ecosystem）项目明确把目标写成加速 RISC-V 开源软件开发、提高平台软件实现质量、协调生态伙伴，并将移动、消费电子、数据中心与汽车列为目标市场。【S3】其成员展示包括 Google、MediaTek、NVIDIA、Qualcomm、Red Hat、北京开源芯片研究院与 ByteDance 等组织。【S3】

这是一条积极信号，但读法要克制。大公司参与项目意味着它们认为共同软件底座值得投入；它不等于这些公司都已有可采购的 RISC-V 机器人平台，也不等于任何一个成员为另一个成员的产品背书。恰恰相反，RISE 的存在告诉我们，RISC-V 最难跨越的门槛已经不是“能否设计一个核”，而是把 Linux、Android、编译器、云原生组件、驱动和开发者工具持续拉到商业质量。

这和 AI 基础设施的经验完全一致。GPU 的护城河并不在一条指令表，而在编译器、通信、数学库、框架后端、调试器、集群运维和开发者迁移成本的复利。RISC-V 可以改变其中 CPU 控制平面的授权结构，却不能绕开这套工程资产的建设周期。

### 6. 高性能、AI 与数据中心：从“可行性展示”到“可规模采购”仍隔着一整套系统

RISC-V 在服务器和 HPC 的讨论很活跃，原因不难理解：高端处理器的设计授权与供应约束很强，开放 ISA 对云、研究机构和主权计算有吸引力。但现有公开证据更适合被理解为“正在推进的工程前沿”，而不是“可替代既有服务器平台的既成事实”。

一篇基于英国 ExCALIBUR 计划的 2024 年研究论文称，自 2022 年初起，研究团队通过 RISC-V 测试床让科学软件开发者试验自身工作负载，并将论文定位为总结现状与待优先解决问题。【S5】这是很有价值的反方证据：即便在愿意投入移植工作的 HPC 社区，采用也需要针对工具链、运行时、库、性能调优和平台软件持续补课。

对机器人公司更现实的拆分是：

- **云端训练主机／集群控制面**：x86 或 Arm 服务器平台仍以软件、虚拟化、驱动、运维与供应支持的成熟度为主导；RISC-V 可以作为探索性开发或特定主权场景的选择，但不应因 ISA 开放而成为训练基础设施的默认替换。
- **AI 加速器控制面**：NPU、DSP、DPU、图像处理器和片上管理单元中，RISC-V 常有结构性吸引力。这里 CPU 核主要运行调度、DMA、固件、设备管理、前后处理或安全监控，需求更容易按特定芯片定制；但 AI 吞吐仍由 MAC 阵列、存储层级、数据流、编译器和算子库决定。
- **端侧应用处理器**：如果机器人需要 Linux、容器、ROS 2、复杂多媒体、GPU/NPU 驱动和长期 OTA，选择 RISC-V 必须以目标 SoC 的 BSP、内核、驱动和软件支持年限为准。ISA 不是采购验收项的替身。

### 7. 机器人和功能安全：研究成果证明方向，不能替代整机责任

RISC-V 与机器人并非纸上关系。arXiv 检索结果中，SentryCore 展示了一个面向汽车、机器人和工业自动化混合关键系统的 RISC-V 协处理器概念：三颗 lockstep 核、ECC 保护数据存储、CLIC 和定时 DMA，并在 Intel 16nm 工艺和多种 RTOS 支持下实现。【S6】另有 Shaheen 的研究原型，将 Linux 能力的 RV64 主核、RV32 处理簇、虚拟化和低功耗 ML 放进一个面向微型无人机导航的异构 SoC；NanoSLAM 则报告在采用 GAP9 的微型无人机上完成低功耗 SLAM 部署。【S6】

这些成果说明三件事。其一，RISC-V 可以成为异构低功耗系统的公共 CPU 接口。其二，实时控制、安全隔离、DSP 与机器学习可以围绕同一 ISA 族组织。其三，开放 RTL 和可定制微架构有利于研究者把时间确定性、功耗和接口共设计。

但研究成果不能被偷换成量产论据。SentryCore 的 lockstep、ECC 与 RTOS 实验并不等于某家机器人供应商拥有 ISO 26262、IEC 61508、ISO 13849 或系统级功能安全证据；Nano-UAV 的功耗和任务也不等于人形机器人在多相机、触觉、关节、长期 OTA、热设计、跌倒保护与售后条件下的可靠性。真正的安全责任最终落在包含电源、传感器、执行器、板卡、软件流程、故障诊断、供应变更和系统验证的产品系统上。

这正是 RISC-V 在机器人中最值得投资的方向与最危险的幻觉同时出现的地方：它让你有机会检查并定制底层；它也把本可由成熟供应商吸收的一部分验证责任转回了自己。

## 三、横向分析：RISC-V 在 ISA 与机器人计算版图中的位置

### 1. 竞争对象不是一组芯片，而是四种不同的经济逻辑

把 RISC-V 与 Arm、x86 和若干 MCU 直接排成“跑分擂台”并不合适。它们首先是不同的 ISA 和生态治理模式；性能要到具体 CPU 核、工艺、缓存、内存、系统软件和工作负载层面才可比较。为机器人战略作横截面分析，更有用的是问：谁拥有接口控制权？谁承担软件和验证责任？谁能让一个 SoC 在交付后稳定工作十年？

| 维度 | RISC-V | Arm | x86 | 封闭／专有 MCU 与 DSP ISA |
|---|---|---|---|---|
| ISA 治理与使用权 | 开放标准；基础 ISA 与已批准扩展为免版税开放构件。【S1】 | 由 Arm 控制的商业授权体系；可购买成熟 IP 与生态入口。 | 由少数既有参与者控制，服务器／PC 生态非常深。 | 多由单一厂商控制，接口、工具和供货与其产品线绑定。 |
| 差异化位置 | 可定制、可自研、可采购多种实现；适合把 CPU 作为 SoC 的一个可塑部件。 | 成熟移动、嵌入式与边缘生态；大量第三方 IP、OS 和工具经验。 | 高性能服务器、桌面和成熟虚拟化／企业软件的惯性最强。 | 低成本、确定性、成熟外设和行业认证路径往往较强。 |
| 开发者的真实代价 | 避免某些 ISA 许可约束，但需要核对实现、profile、BSP、驱动和工具链；碎片化成本可很高。 | 许可成本与路线依赖存在，但“拿到成熟 SoC 就开始做产品”的路径通常更短。 | 采购成本、功耗和板级体积未必最优，但复杂系统软件迁移成本低。 | 平台锁定较重，却可能拥有最完整的外设、RTOS、功能安全和现场支持。 |
| 机器人更适合的位置 | 自定义控制器、传感器网关、加速器管理核、安全协处理器、低功耗边缘 SoC。 | 已量产的主控、视觉／边缘 SoC、较复杂 Linux 端侧系统。 | 训练服务器、开发工作站、部分高功耗机器人主机。 | 电机控制、工业 I/O、安全 MCU、确定性任务。 |
| 不应作出的推论 | 不应把“开放”推导为低风险、低成本或高性能。 | 不应把“成熟”推导为没有锁定或供应风险。 | 不应把“软件成熟”推导为适合所有功耗和成本约束。 | 不应把“确定性强”推导为可承担复杂 AI／多模态系统。 |

RISC-V 的对手不是某一颗芯片，而是这些体系已经积累的交付信用。Arm 的优势常常不是单条指令，而是移动／嵌入式供应链的共同语言；x86 的优势常常不是每瓦性能，而是服务器软件、工具、驱动、工程师和运维流程的惯性；成熟 MCU 的优势则常常是客户不会在量产后才发现 CAN、PWM、编码器、故障诊断或认证资料缺了一页。

### 2. RISC-V 对 Arm：从“许可证自由”走向“系统责任自担”

这是最常见、也最容易失焦的比较。RISC-V 的吸引力来自它把 ISA 的进入权从商业许可关系中抽离出来：企业可自行实现、采购第三方 IP，或者在开放与专有实现之间组合。对于希望掌握长期芯片路线、定制安全机制，或不愿把所有处理器路线绑定在单一授权方上的公司，这种选择权有真实价值。

但 Arm 的竞争力也不能被简化为“付费 ISA”。许多机器人端侧产品面对的是一个已经包含摄像头、ISP、NPU、DDR、PCIe、USB、无线、功耗管理、安全启动、驱动、Linux／Android、RTOS 和量产支持的复杂系统。若采用成熟 Arm SoC，这一整包已经被芯片供应商、ODM 和软件社区在大量产品中踩过。RISC-V 方案若只在 CPU 核上便宜、却要求团队自己解决多媒体、实时、模型部署、容器、安全更新和 FAEs 支持，项目总成本往往会更高。

所以二者不是“开放对封闭”的道德比较，而是**什么时候值得把接口控制权换回自己手里**。当公司有长期、可重复的出货量，有明确的专用工作负载，有维护 BSP／固件／验证的团队，并且某个授权或供应约束确实压缩了利润或路线自由度，RISC-V 的选择权才可能兑现。反过来，若首要目标是尽快把机器人原型稳定量产，成熟 Arm SoC 往往更像风险更小的工程决策。

### 3. RISC-V 对 x86：不是服务器霸主的替身，而是可被嵌入的新控制平面

x86 在训练服务器、开发工作站和企业软件中拥有深厚资产：虚拟化、调试、容器、数据库、中间件、驱动、软件发布和运维经验都已形成路径依赖。RISC-V 从零进入这一层，不只要做出高 IPC 的核，还要证明可扩展性、内存与 I/O、固件、虚拟化、系统库、性能分析、部署工具和商业支持能共同工作。HPC 测试床论文仍将驱动采用所需的高优先级问题作为研究主题，正说明这一现实。【S5】

因此，对人形机器人公司的云训练与仿真平台，RISC-V 在当前更适合研究性或受主权约束的旁路验证，而不是替代训练主机的政策性目标。训练系统最重要的决策变量仍然是 GPU／专用加速器的可得性、网络、存储、框架和工程人员效率；CPU ISA 改变不了 CUDA、通信库、数据管线或大规模集群调度的成熟度差距。

可是在芯片内部，x86 并不是 RISC-V 的真正竞品。NPU、DPU、视觉 SoC、存储控制器和机器人关节控制器不需要把一套数据中心服务器塞进去；它们需要低面积、低功耗、能紧贴 DMA／中断／专用加速器的数据路径的控制核。这里 RISC-V 的可实现性和可定制性很强，且避免把一个受限于既有生态的复杂 CPU 带入每个小模块。它的价值是把“通用计算的接口”嵌入异构系统，不是复制一台服务器。

### 4. RISC-V 对成熟 MCU／DSP：最难跨过的是功能安全与现场维护，而非 ISA

在关节、手部、传感器和电源管理这类节点，工程团队通常优先问：中断时延是否可预测？PWM／ADC／编码器／总线外设是否稳定？故障会不会被检测并进入安全态？RTOS 是否有长期维护？芯片停产后能否持续供货？这些问题中，只有一小部分是 ISA 问题。

RISC-V 可以让团队把自定义指令、实时中断、lockstep、ECC、存储保护或安全监控更紧密地纳入 SoC 方案。SentryCore 等研究表明，这类架构组合是可实现的。【S6】不过，研究样机和可安全量产的控制器之间还隔着诊断覆盖率、失效模式分析、故障注入、工具置信度、软件流程、器件级可靠性、审计材料和长期变更管理。对安全关键节点，采购一个成熟闭环方案的价值，常常正是把这些工作从机器人公司资产负债表上移出去。

所以建议不是“用 RISC-V 取代所有 MCU”，而是把节点分级：

- 对失效可降级、可隔离、可冗余的传感器处理、通信网关和协处理任务，可优先验证 RISC-V 方案；
- 对直接影响人身安全的电机闭环、制动、跌倒保护和高完整性安全岛，应把认证证据、故障机制和量产支持排在 ISA 之前；
- 对于需要极端确定性但工作负载稳定的模块，专用 MCU／DSP 可能仍是 TCO 更优的选择；
- 对需与 NPU、ISP、DSP 共同演进的新型边缘 SoC，RISC-V 可以成为削减架构锁定的一部分，但不应独自承担“安全”卖点。

### 5. RISC-V 对专用 AI 加速器：它可以在芯片里，不等于它提供了 AI 性能

AI 芯片宣传中经常出现“RISC-V＋NPU”“RISC-V AI processor”之类的表述。必须拆开看。RISC-V 核可能负责启动、固件、调度、图编译的一部分控制、DMA、设备虚拟化、传感器预处理或安全监控；NPU／DSP／GPU／CGRA 才承担大规模矩阵和张量计算。二者可以高度协同，但无法相互代替。

这一区分对投资尤其重要。一个标的展示了 RISC-V 向量扩展、开源核或自定义指令，最多说明其 CPU／控制层有定制潜力；它没有自动回答：模型支持哪些算子？量化是否可复现？多相机／触觉数据如何进芯片？显存和片外带宽够不够？编译器是否能稳定生成高效代码？客户是否已经量产？

以机器人为例，RISC-V 更可能在三种情形带来真实价值：

1. **AI 加速器的控制平面**：把模型加载、任务切换、内存管理和设备管理做成可审计、可裁剪的 CPU 子系统；
2. **异构边缘处理**：CPU 负责控制、DSP 负责信号、NPU 负责神经网络，通过清晰的软硬件边界降低功耗；Shaheen 这类研究证明了此种组合的可行性，而非人形机器人量产成熟度。【S6】
3. **特定算法的软硬协同**：对 SLAM、局部规划、滤波或控制等工作负载，如果数据规模和精度固定，可评估向量／DSP／自定义扩展与专用加速器的组合；前提是有端到端实测，不是只报内核峰值。

### 6. 软件生态：RISC-V 已经跨过“没有系统软件”，还没有跨过“默认无摩擦”

最公平的描述是：RISC-V 的上游软件基础已经具备相当可用性，但商业产品的无摩擦体验仍高度依赖具体平台。Linux 内核维护了 RISC-V 的启动、ABI、硬件探测和向量等接口文档。【S4】RISE 将提高平台软件质量列为明确目标。【S3】RVA23 为 64 位应用处理器的二进制生态提供更一致的 ISA 基线，但其范围并不覆盖多数 MCU、机器人外设、NPU ABI 或板级 I/O。【S7】这些都是积极事实。

同时，软件生态的真实体验由更长的链条决定：

```text
ISA / 扩展
    ↓
编译器、链接器、调试器、仿真器
    ↓
Boot ROM、固件、内核、设备树/ACPI、驱动
    ↓
发行版、容器、语言运行时、ROS 2、中间件
    ↓
相机/雷达/电机/网络/NPU/ISP 的 SDK 与诊断工具
    ↓
版本冻结、漏洞响应、现场升级、客户支持
```

RISC-V 的问题主要出现在越往下越“具体”的地方。编译器支持一个目标，并不能保证一个机器人客户的相机驱动、GPU/NPU 运行时、容器镜像、诊断工具和 OTA 机制可用。商业团队需要的不是“能从源码编过去”，而是可复现版本、明确兼容矩阵、故障可定位、补丁有责任主体、长期维护有合同。

开发者选择 RISC-V 的真实理由通常有两类：一类是希望获得芯片设计和 IP 路线自由，另一类是要做极度功耗／面积／功能定制的嵌入式系统。开发者抱怨的也通常不神秘：板卡与 BSP 质量不一、扩展和外设差异、预编译二进制与容器可得性不足、工具性能和调试体验参差、供应商文档与升级承诺不够。RISE 的方向正是修补这一层；它不应被解读为修补已经完成。【S3】

### 7. 当前生态位：它已经是重要“底层选项”，但还不是机器人主计算平台的默认答案

以当前时间截面看，RISC-V 在 MCU、IoT、存储／网络控制、边缘设备和定制 SoC 中最有活力；在高性能应用处理器、服务器和复杂端侧系统中则正从可运行走向可产品化。这个位置既不边缘，也不万能。

它填补的空白是：当公司希望拥有处理器接口的长期控制权，又不想从头定义私有 ISA 时，RISC-V 提供了一条全球可协作的中间路。它的短板是：这一中间路并不自带成熟硬件实现、外设生态、软件支持、质量体系或客户服务。RISC-V International 自己明确只维护标准规范、不提供开放实现；软件分别由相关开源组织与社区维护。【S1】因此，任何商业交付仍需要有人为实现和系统集成负责。

对于人形机器人，最可能形成正循环的不是“RISC-V 跑最大模型”，而是更多机器人边缘 SoC、控制器和加速器把同一开放 CPU 接口用于可复用的软件和工具，进而吸引更多 RTOS、Linux、编译器、验证和芯片团队投入。最容易形成负循环的则是每家公司都声称 RISC-V，却各有一套扩展、SDK、板卡和交付节奏，最终没有任何一个足以成为机器人软件的稳定基线。

## 四、横纵交汇：对人形机器人公司的战略判断

### 1. 历史如何塑造了今天的位置：从“研究自由”到“系统自由的账单”

RISC-V 的历史给了它一项很稀缺的优势：它不是被某家芯片公司用来锁定客户的 ISA，而是被设计成可由共同体维护的开放标准。2010 年的研究动机、2015 年的基金会、2018 年与 Linux Foundation 的协作、2020 年在瑞士的组织化治理，共同塑造了今天的“接口长期可用性”叙事。【S1】这也是它在主权计算、可定制芯片和供应不确定性上具备吸引力的根源。

但同一段历史也塑造了它的弱点。RISC-V 是标准，标准组织不卖成熟 SoC，不替客户签 SDK SLA，不对某款芯片的 errata、驱动、质量或退市负责。开放把价值创造的空间留给生态伙伴，也把整合任务分散给生态伙伴。对研究来说，这是优点；对量产机器人来说，分散责任必须被重新组织成合同、质量体系、版本冻结和事故响应。

所以判断 RISC-V 的成熟度，不能用“规范是否完备”代替“产品是否可交付”。应该问的是：

- 目标硬件实现了哪一个明确 profile 与扩展集合？
- 主线 Linux/RTOS、编译器和调试器的版本如何锁定？
- 电机、相机、网络、加速器和安全组件的驱动由谁维护到何时？
- 故障注入、实时抖动、热、EMI、掉电、OTA 回滚与供应变更由谁承担？
- 如果供应商被收购、停产或改变策略，公司是否真的能拿到足够的 RTL、固件、构建系统、测试资产和授权权利？

这才是“开放”在机器人资产负债表上的翻译。

### 2. 三层架构建议：把 RISC-V 放在它能创造选择权的位置

建议机器人公司的芯片路线采用分层，而非二元站队。

| 层级 | 推荐路线 | RISC-V 的角色 | 不应承担的任务 |
|---|---|---|---|
| 云端训练、仿真、数据处理 | 继续以可验证的 GPU／加速器、网络、存储、框架和集群软件为中心 | 研究性主机／控制面选项；不是近期主路径 | 不应以 RISC-V 名义重构训练基础设施或牺牲研发吞吐。 |
| 机器人主计算与复杂端侧推理 | 按目标模型、功耗、NPU/GPU、驱动、ROS 2、量产支持择优采购 | 在供应商已有成熟 BSP 和加速器栈时可进入评估池 | 不应把 ISA 开放作为 NPU 性能、VLA 支持或交付能力的证明。 |
| 关节、传感器、通信、加速器控制面 | 优先建立 RISC-V 设计与采购能力；从非安全关键或可隔离模块开始 | CPU 子系统、安全协处理、实时控制、DMA／设备管理和专用 SoC 的强候选 | 未有完整安全论证时，不应单独承担人身安全关键闭环。 |

这套分层有一个好处：它避免团队在“完全自研”与“完全采购”之间做虚假的二选一。机器人公司可以把资源集中到自己真正有差异化的控制、传感器融合、硬件软件协同和量产系统，同时保留对 CPU 接口的长期选择权。RISC-V 因而是可组合的底层部件，而不是必须全盘替代的意识形态。

### 3. 投资判断：投资的是价值捕获层，不是 ISA 名称

**结论：不建议以“RISC-V 公司”作为宽泛投资篮子；建议建立一个围绕机器人边缘异构计算的窄观察池。**

优先进入观察池的标的，应同时满足下列至少两类可验证条件：

1. **硬件兑现**：已有首硅、量产、客户设计导入或可复现板级实测，而不是只展示 CPU RTL、FPGA 或路线图；
2. **软件兑现**：有明确 SDK、编译器／RTOS／Linux 支持、驱动版本、调试工具和客户可复现模型／控制任务；
3. **实时与安全兑现**：能提供 lockstep、ECC、隔离、故障诊断、时延抖动、故障注入、工具链与认证计划的完整证据；
4. **机器人相邻性**：产品已进入相机、关节、工业控制、低功耗感知、机器人边缘盒或 AI 加速器控制面，而非只在通用开发板上演示；
5. **权利与供应兑现**：RTL、固件、编译器修改、验证资产和第三方 IP 的权属清晰；代工、封测、存储、外设和长期供货有可审计安排。

应避开的三种交易叙事也很清楚：

- 把“采用 RISC-V”包装为“拥有完整 AI 芯片能力”；
- 把开源核或公开 ISA 包装为“无需软件／验证投入”；
- 用单个 benchmark、开发板启动或学术论文替代客户量产和安全证据。

真正可能获取长期价值的环节包括：可复用且可审计的实时／安全 IP，面向异构 SoC 的编译与部署工具，机器人传感器和执行器的驱动／诊断平台，硬件验证／故障注入／测试工具，以及在特定低功耗任务中形成客户锁定的完整 SoC。纯粹、同质化的通用 CPU IP 则很可能面临价格竞争，因为 ISA 开放降低了进入门槛，也减少了“仅凭指令集收租”的空间。

### 4. 并购判断：买“可转移的工程资产”，不买“开放的名义”

**结论：当前不应启动以获得 RISC-V ISA 为目的的并购；可对小而专的安全／实时／软件资产进行机会型并购或人才收购。**

原因很直接：ISA 不需要被买下，基础标准本身可使用。【S1】整家公司并购的价值只有在其拥有稀缺、可转移且已被交付验证的资产时才成立。例如：经过量产验证的关节控制 SoC 与固件团队、可移植的安全岛 IP 与验证资产、能把模型从框架稳定部署到特定 NPU 的编译／运行时团队、或者长期维护机器人边缘 Linux／RTOS 的系统软件团队。

并购前的 P0 问题不应是“它是不是 RISC-V”，而是：

- RTL、微码、固件、SDK、编译器改动和测试用例是否由标的完整拥有，还是依赖不可转让的第三方许可？
- 关键工程师是否是把驱动、bring-up 和客户问题串起来的隐性单点？他们的留任成本与代码资产是否相称？
- 已披露的客户到底买的是芯片、模组、项目交付还是联合研发服务？收入能否随控制权变更转移？
- 质量与安全资料是否完整到能支持下一轮认证和客户审厂？
- 若终止与原供应商合作，代工、封测、DDR、PHY、EDA、RTOS 或安全组件的替代计划是否存在？

如果这些问题没有答案，“买到 RISC-V”只会变成买到一套需要持续烧钱维护、但没有产品闭环的工程分支。

### 5. 自研判断：有窗口，但窗口在子系统，不在通用 CPU 竞赛

**建议的自研窗口：**

- RISC-V 作为自研 NPU／DPU／视觉 SoC 的管理核、安全岛或可编程前后处理核；
- 面向关节、手部、传感器和通信的低功耗控制子系统，前提是需求稳定、出货可预期、外设和实时架构存在明确差异化；
- 围绕机器人工作负载的模型部署、实时诊断、功耗管理和安全监控软件，而不是重复造一套泛用 Linux 发行版。

**不建议的自研窗口：**

- 为了“自主 ISA”从零打造可与成熟 Arm／x86 应用处理器竞争的通用高性能 CPU；
- 在没有自有加速器、明确数据流和长期软件投入前，自研“RISC-V AI 芯片”；
- 先做芯片再寻找机器人工作负载，期待 ISA 标签自然形成客户需求。

判断公式可以写得很朴素：

> 自研净价值 = 可避免的长期许可／供应／BOM 成本 + 由紧耦合带来的性能或功耗收益 − CPU/IP 集成 − 软件维护 − 验证／安全 − 量产与机会成本。

其中最常被低估的两项是软件维护和验证／安全。开放 ISA 不会把它们变成零；有时反而让公司必须更主动地把它们变成自己的能力。只有当上式在一个明确的机器人子系统、明确的生命周期和明确的出货规模下为正，自研才是战略而不是偏好。

### 6. 三个未来剧本

#### 最可能剧本：RISC-V 成为机器人异构芯片里的“默认可选控制核”

在这个剧本中，Linux、编译器、profile 和 RISE 推动的平台软件逐步改善，RISC-V 在 MCU、控制面、NPU/DPU、传感器与低功耗边缘 SoC 中继续扩张。Arm 保持复杂应用处理和大量成熟 SoC 的领先，x86 保持云端研发与服务器控制的惯性。机器人公司在局部模块采用 RISC-V，但不会把整机算力押注在单一 ISA 上。

这是最符合历史路径的结果：标准开放性产生设计空间，软件生态逐步收敛，价值沉淀在实现者和系统集成商手中。对本库的研究目标而言，重点是捕捉那些已经把“可选控制核”转化为真实 BOM、实时能力、软件资产和客户交付的公司。

#### 最危险剧本：碎片化和“开放幻觉”吞掉成本优势

在这个剧本中，各 SoC 厂商以定制扩展、私有 SDK 和不一致的 BSP 为差异化手段。开发者得到的是越来越多的 RISC-V 名称，却没有稳定的软件基线；机器人公司为了供应多元化引入多个平台，最终维护多套内核、驱动、工具和安全流程。安全关键模块由于认证与责任链薄弱，仍不得不回到成熟 MCU／SoC。

危险不在于 RISC-V 不够开放，而在于开放没有被 profile、标准测试、长期维护和商业责任组织起来。历史上，RISC-V 为扩展留下空间是正确选择；今天，如果生态不能把空间变成兼容性，早期的自由会成为后期维护负担。对投资人而言，这会让许多“RISC-V 生态公司”只有项目收入，没有可扩张的平台毛利。

#### 最乐观剧本：安全、实时、边缘 AI 的开放平台出现可复用基线

在这个剧本中，实时中断、安全岛、虚拟化、内存保护、RTOS、机器人中间件和边缘 AI 部署工具出现跨芯片可复用的组合；一批 SoC 将 RISC-V 控制面与 NPU／DSP／传感器接口做成经过量产验证的平台。机器人公司可以在不完全依赖单一 ISA 授权方的前提下，替换部分控制与边缘计算部件，并保留主计算的成熟供应路径。

这不是“RISC-V 取代 Arm／x86”，而是开放接口第一次把机器人异构计算中的系统成本降到值得大规模采用的程度。触发条件不是某个单核跑分，而是：可审计的安全资料、可重复的实时性能、长期 BSP／SDK、可迁移模型工具、稳定供应和多家客户的量产证言同时出现。

### 7. 给管理层的行动清单：先做验证，再谈路线下注

未来两个产品周期内，建议把 RISC-V 作为一个跨硬件、软件和供应链的验证课题，而不是单独的芯片立项。

| 优先级 | 建议动作 | 成功标准 | 失败／退出条件 |
|---|---|---|---|
| P0 | 建立“机器人 RISC-V 采用基线”：针对关节、传感器、NPU 控制面列出 ISA/profile、RTOS/Linux、外设、实时、安全、SDK 和供货要求。 | 每个候选芯片可用同一张验收表比较，而不是听厂商演讲。 | 无法拿到具体实现、BSP、生命周期和安全资料的候选直接退出。 |
| P0 | 选择一个失效可隔离的模块做双路径 PoC：RISC-V 方案对比成熟方案。 | 用端到端延迟抖动、功耗、故障恢复、开发工时、BOM、工具稳定性和可维护性测算 TCO。 | 只做核级 benchmark，或无法复现驱动／OTA／诊断流程，不进入量产评审。 |
| P1 | 对自研加速器／控制器明确“RISC-V 在哪里、非 RISC-V 在哪里”的架构边界。 | CPU 控制面、DMA、调度、安全岛和 NPU 数据面职责清楚；模型性能由实际工具链证明。 | 把 ISA 替代成 AI 性能论据，或没有软件负责人和验证预算。 |
| P1 | 建立投资与并购观察池，集中在安全实时、边缘 SoC、工具链、验证测试四类资产。 | 有芯片／客户／软件／权属中的至少两项强证据，且可与机器人路线形成明确协同。 | 只有 RTL、融资新闻、合作意向或开发板展示时，不进行高溢价交易。 |
| P2 | 参与或跟踪 RISE、RISC-V International、Linux／RTOS 相关工作组。 | 获得对 profile、工具链和供应商路线的早期信息，并形成工程影响力。 | 若投入仅停留在会议赞助、无法换来代码、标准或供应支持，应收缩。 |

行动的顺序很重要。先从一个可隔离模块验证端到端工程收益，再把结果扩展到自研 SoC 或资本动作；不能因为标准足够开放，就跳过系统软件、功能安全和供应链的尽调。人形机器人不是一块开发板，量产后每一条固件链路、每一次故障处理和每一颗替代料都会回来向架构决策收费。

## 五、证据、冲突与待验证事项

### 1. 证据等级与相反证据

| 命题 | 支持证据 | 反对／限制证据 | 当前判断 |
|---|---|---|---|
| RISC-V 是可长期采用的开放 ISA 基础 | 官方组织说明其为开放标准、基础 ISA／已批准扩展免版税、组织不经营商业产品。【S1】 | 开放标准不能替代实施质量、供应链和系统软件。 | 高置信度；仅限 ISA 与治理层。 |
| RISC-V 软件生态正在向商用成熟度推进 | Linux 维护 RISC-V 架构文档；RISE 明确以平台软件质量和商用准备为目标。【S3】【S4】 | RISE 的目标本身说明生态仍需协调；内核支持不证明具体 BSP／驱动可量产。 | 中等置信度；应按芯片、发行版和工作负载逐项验收。 |
| RISC-V 适合机器人实时／安全与低功耗异构探索 | SentryCore、Shaheen、NanoSLAM 等研究给出技术可行性与具体原型。【S6】 | 均非人形机器人量产、功能安全认证、长期 OTA 或大规模客户证据。 | 中等置信度；适合 PoC 与非安全关键模块的工程验证。 |
| RISC-V 可以短期替代训练／HPC 主机平台 | 有 HPC 测试床与研究投入。【S5】 | 论文将重点放在仍需解决的采用问题；AI 训练的主要瓶颈并非 ISA。 | 低置信度；不建议作为近期基础设施主路径。 |

### 2. 需要持续追踪的开放问题

1. 面向机器人边缘应用的 RISC-V profile、实时中断、安全扩展、IOMMU／虚拟化与工具链，是否已经形成可被多家 SoC 共同采用的稳定基线？
2. 目标供应商是否能给出量产 SoC 的长期 BSP、漏洞修复、OTA、驱动、外设兼容矩阵和故障处理 SLA？
3. 对直接控制关节或安全岛的方案，故障诊断、lockstep／ECC、时延抖动、失效模式、工具链与认证资料是否能通过独立审查？
4. 自研或并购时，RISC-V 核之外的关键 IP——DDR／LPDDR、SerDes、PCIe、USB、以太网、ISP、NPU、EDA、RTOS 与安全组件——是否构成新的供应或许可单点？
5. RISC-V 在机器人 VLA 端侧推理中究竟是控制核、CPU 前后处理，还是参与主计算？每个角色的功耗、内存与软件收益是否有端到端数据？
6. RISE 成员参与、标准工作组席位、合作新闻和开发板发布，是否能转化为客户订单、可靠软件版本和持续维护承诺？未经验证不得将前者当作后者。

### 3. 产业链分类结论

本库当前分类没有、也不应仅为 RISC-V 新增“RISC-V 芯片”类别。原因是 RISC-V 是横跨 MCU、CPU IP、服务器 CPU、NPU 控制核、DPU、存储控制器和边缘 SoC 的 ISA；它不是一种稳定的收入承载物，也不能用来判断一家公司的 AI 芯片主价值创造。

因此，本技术应归入 `wiki/technologies/`，作为评估 CPU 控制面、可编程性、供应／IP 与系统软件风险的共用技术页。公司仍按其已商业化主产品归入 GPGPU、TPU、NPU、DPU、边缘 SoC、加速计算平台或其他既有分类；公司采用 RISC-V 只能作为产品架构和尽调维度，不可替代主分类证据。

## 方法论说明

本报告采用横纵分析法：纵轴追踪 RISC-V 从伯克利研究项目、标准化组织到软件生态协作的演进，横轴比较其与 Arm、x86、成熟 MCU／DSP 和 AI 加速器控制面的差异，再将两条轴交汇到人形机器人公司的采购、自研、投资和并购选择。判断与建议均明确标为研究者推断；事实性断言以可回溯来源为边界。
